# Auth0 lifecycle delivery and owner recovery research

Date: 2026-09-28. Code baseline: `beed231`. Scope: ACC01.3–ACC01.4 in the report access plan. This is official-documentation research and a proposed implementation contract, not evidence of a configured or accepted Auth0 tenant. No tenant, message, credential, provider mutation, build or test was created or run for this research.

## Decision

Build separate adapters for the documented transports; do not implement a supposed universal Auth0 signed security webhook. Auth0 Event Streams support a configured bearer credential over HTTPS, custom Log Streams support a configured Authorization header, and OIDC Back-Channel Logout uses a signed logout JWT. Their payloads, delivery rules and coverage differ. A project-authenticated password Action callback would be our own integration, not a native Auth0 webhook signature feature.

The safe local work is bounded parsing/authentication, durable event deduplication, identity/session fencing, replay/checkpoint recovery, and truthful blocked/uncertain receipts. Production activation still requires demonstrated coverage and delay handling for all enabled Dashboard/API/self-service mutation paths. Lost-factor recovery additionally needs an approved owner-verification and pending-recovery admission policy. Existing fresh-OTP proof does not itself prove that the legitimate owner completed a particular recovery intent.

## Existing implementation boundary

These are code observations, not Auth0 claims:

- `backend/src/UnitToko.Platform/Identity/AccountRecoveryService.cs:24` authorizes an owner with fresh MFA or another actor with current System `recovery.initiate`. Lines 35–54 increment the target security version/fence, revoke local sessions and insert an encrypted **blocked** provider intent in one Mongo transaction. The service sends nothing and accepts no replacement password/factor secret.
- For self-recovery, the protected actor security version is intentionally the pre-change version, while the intent records the post-change version. A dispatcher must validate that exact transition and its durable intent. Requiring the old version to remain current would make legitimate self-recovery impossible; accepting any later version would permit stale authority.
- `backend/integrations/auth0/v1/01-request-otp.cjs:27` challenges an existing OTP factor or requests enrollment when none exists. `02-assert-otp.cjs:16` requires newly completed OTP evidence. These drafts establish authentication assurance, not evidence of recovery ownership or approved factor replacement.
- `backend/src/UnitToko.Platform/Identity/IdentityAdmission.cs:28` admits an existing active identity with validated proof and active membership. It currently has no recovery-specific pending-admission state. Add that policy atomically with any future factor-reset dispatch; do not reinterpret an old blocked intent as a new login prohibition without an explicit migration/policy.
- The ACC01 contracts in `docs/superpowers/plans/2026-09-28-report-access.md:73` are internal normalization targets. `ProcessAsync(...)->bool` currently describes false as a duplicate only; an implementation also needs an explicit safe outcome for an authenticated unknown subject or irrelevant event. Do not overload false to claim that every ignored message was a duplicate.

Preserve the existing 30-minute idle, eight-hour absolute and five-minute sensitive-action factor defaults. Do not merge accounts by email, reactivate local membership from a provider profile, or alter immutable historical actors.

## Verified provider capabilities and limitations

### Delivery mechanisms

| Mechanism | Verified official behavior | Implementation consequence |
| --- | --- | --- |
| Event Streams webhook | The documented webhook destination sends HTTP POST and supports `webhook_authorization.method = bearer` with a configured token. AWS EventBridge and Auth0 Actions are separate destinations. Setup still labels the Dashboard area “Event Streams (Early).” [Create an Event Stream](https://auth0.com/docs/customize/events/create-an-event-stream) | Authenticate the configured credential before interpreting data; bind the receiver configuration to one issuer/tenant/stream. This is bearer authentication, not a per-message signature. Never take the trustworthy issuer from an arbitrary payload field. |
| Events API | Management API `GET /api/v2/events` uses SSE and `read:events`. It supports an opaque resume offset, `Last-Event-ID` or `from`, `from_timestamp`, and offset-only markers; expired offsets are possible. Connections may cycle. The SSE message ID is a checkpoint, distinct from the enclosed event ID. [Events API](https://auth0.com/docs/customize/events/consume-events-with-events-api) | A server-only authenticated pull consumer avoids a public inbound credential, but retains coverage/lag limitations. Persist progress only after preceding effects commit. Do not reset an expired checkpoint to “now” and silently skip the gap. |
| Custom Log Stream | HTTPS POST with a valid certificate; the configurable Authorization header is optional in Auth0. JSON lines/arrays/objects are selectable. [Custom Log Streams](https://auth0.com/docs/customize/log-streams/custom-log-streams) | Require a nonempty strong credential in Unit Toko configuration; choose one bounded format and verify an actual tenant fixture. No permissive parser that guesses every possible wrapper. The API schema lists JSONLINES/JSONARRAY, which reinforces pinning the configured format. [Create log stream](https://auth0.com/docs/api/management/v2/log-streams/post-log-streams) |
| Log Management API | Checkpoint retrieval follows `log_id`, not event time, to avoid skipping delayed records. It returns at most 100 logs per request; `from`/`take` checkpoint mode ignores other query parameters. Use the returned next link. [Retrieve logs](https://auth0.com/docs/deploy-monitor/logs/retrieve-log-events-using-mgmt-api) | This is the reconciliation path for retained logs. Filter allowed security event types locally after fetching; do not assume a `q` filter limits checkpoint results. Pin next-link origin/path before attaching Management API credentials. |
| OIDC Back-Channel Logout | Enterprise entitlement; a signed logout JWT identifies the subject/session. [Back-Channel Logout](https://auth0.com/docs/authenticate/login/logout/back-channel-logout) | Reuse maintained JWT validation with pinned issuer/client and JWKS handling, correct logout event claim, time validation, no nonce and durable replay control. Treat session logout separately from an account-wide password/factor event; a logout token is not a generic security-change envelope. |
| Post-change-password Action | Runs for database users after password changes/resets, asynchronously and without blocking completion. [Post Change Password](https://auth0.com/docs/customize/actions/explore-triggers/post-change-password) | A custom authenticated callback can improve password notification latency, but cannot veto the change or independently guarantee durable delivery. Do not copy the documentation’s email-based lookup example into our identity binding. |

**Log-stream limitation is material:** Auth0 explicitly positions logs for monitoring/analytics and advises against using them in the application’s critical path or for real-time decisions. Delivery may be out of order. Its documented delivery process makes up to three attempts, repeats errored delivery, and pauses the stream after seven consecutive unreachable days. These facts do not establish a maximum security-event delay. [Log Streams](https://auth0.com/docs/customize/log-streams)

Event Streams have different rules: duplicates and reordering are possible; four total attempts are documented with retry delays of 1, 2 and 4 seconds; HTTP 4xx fails without retry. Exhausted delivery requires recovery. The same page lists both three consecutive failed attempts and 500 consecutive/5000 total failures as disable conditions. Treat this as a documentation ambiguity to verify, not a reliable outage budget. [Events Best Practices](https://auth0.com/docs/customize/events/events-best-practices)

Auth0 provides delivery-failure inspection and single/batch redelivery APIs. Monitoring guidance recommends checking delivery failures every five minutes; that recommendation is not a revocation SLA. A disabled stream requires operational recovery. [Event failure recovery](https://auth0.com/docs/customize/events/event-testing-observability-and-failure-recovery)

Back-channel delivery has a five-second response timeout; HTTP 400 is recorded and not retried for that session. The configuration page’s older troubleshooting statement about only standard logout contrasts with the dedicated initiators page; use the latter for configurable initiators and verify actual behavior. [Back-channel configuration](https://auth0.com/docs/authenticate/login/logout/back-channel-logout/configure-back-channel-logout)

| Change/source | Verified signal | Remaining acceptance boundary |
| --- | --- | --- |

[API-triggered Action](https://support.auth0.com/center/s/article/post-change-password-Action-trigger-is-executed-when-the-user-s-password-is-updated-using) | Verify Dashboard reset/change paths and actual callback/log payloads in the selected database connection. A reset request is not a completed change. |
| Password completion/request logs | `scp` means successful password change; `scpr` means successful change-password request. `gd_enrollment_complete`, `gd_unenroll` and `gd_update_device_account` describe completed enrollment, removal and device update. [Log filters and codes](https://auth0.com/docs/customize/log-streams/event-filters) | Map only verified target identifiers and exact allowlisted types; do not treat starts, failed actions or generic success as completion. | Dashboard MFA reset | Official support directs administrators to `gd_unenroll`; `details.auth.subject` identifies the **administrator who initiated** the reset. [Dashboard reset attribution](https://support.auth0.com/center/s/article/Performed-MFA-reset-action) | Never use the administrator’s ID as the affected end-user. | Administrator account block; user deletion | The `user.updated` schema contains `data.object.user_id`, `blocked`, previous object, time, event ID and tenant/stream metadata. The user event catalog also lists deletion. Demonstrate both Dashboard and API paths. The published schema alone is not a guarantee that every mutation emits an event. |
| Profile update vs password/factor mutation | Auth0 says `user.updated` is not one-to-one with API calls and excludes updates involving only login/last-IP/update-time counters. [Excluded fields](https://support.auth0.com/center/s/article/fields-excluded-from-user-updated-auth0-event-stream-trigger) | Do not infer that every password change or MFA replacement is fully represented by the remaining profile fields. A `multifactor` array is not verified factor-completion evidence. |
| Provider block vs attack-protection block | Administrative blocking prevents new login. Brute-force blocking is separate and does not set profile `blocked: true`. [Administrator blocks](https://auth0.com/docs/manage-users/user-accounts/block-and-unblock-users), [Brute-force blocks](https://support.auth0.com/center/s/article/Query-users-blocked-by-brute-force-protection-using-the-management-API) | Failed login or a blocked identifier is not sufficient evidence to disable an arbitrary local user. Never resolve by submitted email. Provider unblocking must not silently reactivate locally suspended access. |
| Back-channel initiators | Explicit values include password change, session expiration/revocation, account deletion and email-identifier change. Factor reset and account block are not listed. [Initiators](https://auth0.com/docs/authenticate/login/logout/back-channel-logout/oidc-back-channel-logout-initiators) | Do not label back-channel logout as complete factor/disable coverage. Explicitly configure and accept the selected initiators; a sid-scoped logout does not prove an account-wide factor change. |

The password Action event schema exposes optional `user.user_id`, `last_password_reset`, and optional `transaction.correlation_id`; the latter can originate in the application’s authentication request. It does not document a mandatory globally unique immutable security-event ID or a Unit Toko recovery-intent claim. [Password Action event schema](https://auth0.com/docs/actions/reference/post-change-password/post-change-password-event-object) Therefore, a custom callback needs its own reviewed envelope, credential/signature rotation, replay policy and fallback reconciliation. A caller-provided correlation string alone cannot authorize recovery completion, and a timestamp is not a collision-free event ID.

## Proposed local adapter contract

The following are project design recommendations, not vendor guarantees:

1. Keep transport verification separate from event normalization. Suggested adapters are `Auth0CloudEventReceiver`, `Auth0LogReceiver`/`Auth0LogCheckpointReader`, and an independent `Auth0BackChannelLogoutReceiver`. All are disabled until their required issuer, transport credential, limits and tenant acceptance record exist. A project-specific Action receiver is optional and explicitly named as custom.
2. Authenticate before parsing sensitive content. Use strict bounded JSON, reject duplicate key ambiguities, exact permitted event types, native field types and excessive nesting/batches. Match configured tenant/stream metadata where supplied, then derive the issuer from trusted configuration. Use constant-time comparison of the configured bearer secret and support deliberate overlapping secret rotation; never log it. A native bearer-authenticated webhook is valid without an invented signature header. Machine endpoints require their own auth policy rather than browser cookies/CSRF, and must not weaken browser route protections.
3. Normalize only an established target subject. Use issuer plus the full provider user ID. Unknown subjects cannot create profiles/memberships or expose existence; record only a minimal non-disclosing outcome. Do not accept `details.auth.subject` or an email as an end-user substitute. Redact provider bodies before diagnostics; broad authorization history must not contain raw names/emails, reset links, tokens or encrypted delivery payloads.
4. Namespace durable IDs, for example `log:<log_id>`, `event:<event.id>` and `logout:<jti>`, under the exact issuer. A single event arriving through push and reconciliation deduplicates by its real source ID. Different transports may describe the same change with different IDs; conservatively applying revocation twice is safer than an invented email/timestamp merge. Keep same-ID/different-body anomalies detectable with a canonical safe-field digest. Reject or quarantine them without changing prior committed evidence.
5. In one Mongo transaction, insert the unique event record, conditionally advance the current identity security version and shared fence, revoke the relevant local sessions, and write a minimal immutable audit. Account disabling/deletion also needs a persistent admission hold with explicit provenance. A session-only logout must touch the same session fence used by business writes and target the validated sid; do not blindly increment the global account epoch for every routine logout.
6. Acknowledge accepted security events only after their revocation/fence transaction commits. If a durable inbox is used to absorb spikes, either apply the admission/session hold on acceptance or describe it as **queued**, with no claim that revocation is complete. Use a retryable server response on unavailable persistence. For batches, do not acknowledge uncommitted entries; committed entries must replay safely.
7. Persist the checkpoint after all earlier effects commit; offset-only progress cannot leap over unfinished work. Do not drop old but unseen authenticated changes solely because their event time predates the most recently received event. No late unblock/enrollment can clear a local hold or lower security versions. Conservative late revocation may require another login; that is not proof that the latest session was compromised.
8. Monitor receive delay, consumer checkpoint lag, disabled streams, unknown schemas, delivery failures and the available replay horizon. An expired cursor/retention gap creates a visible coverage failure, not an empty successful result. Decide and test the fail-closed scope and accepted lag before launch. No asynchronous adapter can retroactively stop a business commit that finished before its event arrived.

The internal `VerifiedProviderSecurityEvent` constructor must remain inaccessible to HTTP DTO binding and test-only shortcuts. An enum/result such as `Applied`, `Duplicate`, `IgnoredUnknownSubject`, `IgnoredUnrelatedType` is clearer than boolean overloading; only the first two prove a recognized security event was processed. Public responses can remain non-disclosing.

## Owner recovery and dispatch

### What the provider proves

The password-ticket endpoint starts a reset journey; Auth0 explicitly says it does **not** verify the user’s identity. It accepts a user ID, expiry and client selection; `client_id` is required for the Password Reset Post Challenge trigger. A generated URL is a secret and a successful response means ticket creation only. Keep `mark_email_as_verified` false and omit email from redirects. [Password ticket API](https://auth0.com/docs/api/management/v2/tickets/post-password-change)

Password Reset Post Challenge runs after the first challenge but before a new password is set. It is blocking, requires Universal Login, and can demand another factor or redirect to a verifier. It is a useful ownership/risk gate, **not** a password-change completion event. [Post Challenge](https://auth0.com/docs/customize/actions/explore-triggers/password-reset-post-challenge)

Auth0 MFA reset removes enrollment, allowing the user to enroll again as a new user at the next login. The provider documents administrator reset when a user lacks both device and recovery code. Recovery-code login is a distinct path. [Reset MFA](https://auth0.com/docs/secure/multi-factor-authentication/reset-user-mfa) This documentation does not define Unit Toko’s independent owner-verification policy. A newly enrolled OTP can demonstrate possession of the newly created factor without establishing that its registrant was the legitimate pre-reset owner.

### Safe implementation boundary

- Dispatch must re-read the durable intent, exact bound issuer/subject, active local identity and initiating authority. For self-recovery, accept only the recorded before→after epoch transition and unchanged grant authority; an unrelated later security change invalidates dispatch. For an operator request, check current System permission and epoch again. Do not send to an operator-entered address or reveal a reset ticket to an administrator merely because they may initiate recovery.
- Atomically claim a specific intent revision before the network call. Provider acknowledgement can advance an attempted/accepted state, never `completed`. A timeout is uncertain. The documented ticket API does not establish caller-supplied idempotency semantics; do not fabricate an Idempotency-Key guarantee or automatically create more tickets after an ambiguous response. Reconciliation/reissue is an explicit reviewed state transition. Provider ticket issuance and actual email delivery are also distinct outcomes.
- A pending factor-recovery hold must be enforced inside the same admission/session-creation transaction. Only a narrow recovery challenge may proceed; it grants no ordinary business session or System role. Bind one-use state to intent, exact account, current security/grant revisions, expiry and allowed destination. The browser supplies no authoritative user, recovery epoch or completion status.
- Keep two pieces of evidence distinct: **the provider observed a security change** and **the owner reverified for this intent**. A generic OIDC `ProviderIdentityProof`, matching email, success query parameter, redirect landing, ticket creation or newly enrolled factor is insufficient to assert intent completion. Completion needs a reviewed, authenticated correlation from the chosen provider journey, plus the required owner verification and normal fresh-factor checks. If that correlation cannot be established, report owner reauthentication separately and leave recovery completion unconfirmed.
- A change event caused by the intended recovery will itself advance the local security epoch. Completion must consume exact trusted evidence that associates the expected transition with this intent; allowing “any newer epoch” or “same user since request time” would also admit unrelated changes. The published generic Action correlation field does not solve this. Do not invent proof in fixtures and call it an Auth0 capability.
- Lost-factor ownership, independent staff checks, acceptable recovery factors, rate limits and approval expiry are business/security decision gates. An administrator may initiate the reviewed process, not choose a replacement password/factor or bypass owner verification. Until accepted, keep actual factor removal and owner completion unavailable; local administration, blocked receipts and other modules can continue.

## Entitlements and operational gates

Current public pricing lists Event Streams across plans (1/3/4/8 destinations in the displayed Free/Essentials/Professional/Enterprise comparison), paid log-stream allowances, and Enterprise-only OIDC Back-Channel Logout and Prioritized Security Log Streams. This is not confirmation of this project’s B2B contract, tenant availability or cost. [Pricing](https://auth0.com/pricing) The Events API separately documents concurrent connection limits of 1 Free, 4 self-service and 8 Enterprise; do not confuse connection limits with destination allowances. [Events API](https://auth0.com/docs/customize/events/consume-events-with-events-api)

Prioritized Log Streams include a predefined attack-protection/SMS-related subset, not all password/MFA lifecycle records. Buying that feature does not establish complete lifecycle coverage. [Prioritized stream scope](https://support.auth0.com/center/s/article/Prioritized-Log-Stream)

The current log-retention page lists one day for Starter, five for B2B/B2C Essentials, ten for B2B/B2C Professional and thirty for Enterprise, and explicitly warns that tenant logs are not real-time. [Log retention](https://auth0.com/docs/deploy-monitor/logs/log-data-retention) Confirm actual tenant retention before setting local outage/replay limits. The reviewed Events API guide does not provide a specific offset-retention duration; obtain and test that separately rather than borrowing the log-retention number.

External acceptance remains open for exact tenant/region/issuer/client/connection, commercial entitlement, Action ordering and actual factor evidence, event payloads for every permitted mutation API, credential rotation, sender/domain configuration, Management API scope/rate limits, HTTPS edge behavior, operational response to lag/gaps, and owner-proof completion. No purchase or provider configuration is authorized by this research.

## Focused acceptance cases for implementation

These are required future checks, not tests executed here:

| Boundary | Required evidence |
| --- | --- |
| Transport and identity | Missing/wrong/rotated credential, wrong tenant/stream, unknown subject, malformed native types, oversized batch and target-vs-administrator ambiguity are denied or safely classified without creating accounts. Actual sanitized tenant fixtures are separate from synthetic fixtures. |
| Atomic effect | Two receivers deliver one real source ID concurrently; one event/audit is committed. A sensitive transaction paused before its fence conflicts with password/factor/disable processing. Rollback leaves no partial revocation or acknowledged event. |
| Ordering and delivery | Late events, push plus checkpoint replay, same-ID/body conflict, failed persistence, partial batch, disabled stream, expired offset, retention gap and reconnect after host restart. No duplicate lowers an epoch or clears a hold; no checkpoint skips unfinished effects. |
| Complete source matrix | Password reset/change, OTP enrollment/replacement/removal/reset, admin block/unblock and deletion through owner flow, Dashboard and each enabled Management API. Measure receive/revocation delay across two API hosts; do not infer API coverage from one Dashboard case. |
| Recovery ownership | Wrong owner/intent/epoch, expired/replayed state, unrelated later security change, admin reset followed by attacker enrollment, recovery-code login, cancelled factor challenge, and successful authentication without a confirmed provider change. No weak business session or fabricated completion. |
| Dispatch truthfulness | Disabled config remains blocked; self-request survives only its own documented epoch transition; authority revocation prevents sending; timeout stays uncertain; duplicate workers cannot blindly resend; tickets/emails/secrets do not appear in broad history, URLs, browser storage or receipts. |
| Tenant acceptance | Verify real sender and owner journey, provider events and Action outputs, rather than marking isolated provider fixtures as live Auth0 success. Resolve the documented event auto-disable ambiguity and the pending-recovery policy before production activation. |

ACC01.3 can implement the verified transport-specific local boundary now while retaining the external coverage gate. ACC01.4 can implement safe blocked/uncertain orchestration and admission-hold mechanics, but actual delivery and completed owner recovery remain gated by the accepted provider journey and ownership evidence. These gates do not stop unrelated local procurement modules.
