# Module boundaries during the production migration

The repository has three main source directories: `frontend`, `backend` and `docs`. Maintained workflows use **Next.js/TypeScript → .NET 10 API → MongoDB**, with separate worker and private-evidence owners. The C# service already owns locally connected catalog/ordering, fulfillment/invoicing, payment review/allocation, procurement and stock/accounting workflows; it is no longer only a future replacement. Each workflow's actual implementation, local evidence and outstanding acceptance are recorded in the [single progress ledger](../quality/production-progress.md), including all original requirements and the [97-item register](../requirements/unit-toko-report-2026-09-28.md).

## Current ownership

| Owner | Source | Responsibility |
| --- | --- | --- |
| Frontend routes and presentation | [app](../../frontend/src/app/), [components](../../frontend/src/components/), [modules](../../frontend/src/modules/) | Pages, forms, immutable review displays and scoped workspace navigation; browser controls do not grant authority |
| Browser API contract | [typed client](../../frontend/src/api/client.ts), [generated schema](../../frontend/src/api/generated/schema.ts), module-specific clients | Exact `/api/v1` DTOs, reviewed actor/version/binding, explicit commands and original-key recovery; generated types come from [backend/contracts](../../backend/contracts/) |
| API boundary | [UnitToko.Api](../../backend/src/UnitToko.Api/) | HTTP contracts, OIDC/session/CSRF/origin boundaries, release-profile endpoint composition and scoped response projections |
| Domain modules | [UnitToko.Modules](../../backend/src/UnitToko.Modules/) | Typed contracts, invariants and calculations for Identity, Organizations, Catalog, Ordering, Inventory, Fulfillment, Billing, Procurement, Accounting and Documents |
| Application and persistence owners | [UnitToko.Platform](../../backend/src/UnitToko.Platform/) | Business services, current authorization, source/provenance checks, Mongo transactions, schemas/migrations, idempotency, audit/outbox, identity and private storage adapters |
| Background and isolated processing | [UnitToko.Worker](../../backend/src/UnitToko.Worker/), [UnitToko.ImageDecoder](../../backend/src/UnitToko.ImageDecoder/), [document-processing assets](../../backend/document-processing/) | Explicit migration command; configured outbox/evidence/OCR consumers; bounded decoding and extraction from assigned private originals |
| Retained legacy authority | [backend/legacy](../../backend/legacy/) | Existing TypeScript domain, server, libSQL persistence, documents and SQL migrations retained for unretired adapters and regression evidence; not the Release 1 pilot's writer |
| Documentation and acceptance | [docs](../), [ledger](../quality/production-progress.md) | Requirements, module/security contracts, operator runbooks and distinct local/staging/production evidence |

A frontend review or generated DTO is not business approval. The owning C# service rechecks current scoped authority and genuine source records, and coordinates its persistent effects within the transaction. Historical reads and operation recovery retain their own authorization/provenance requirements. Cross-module code must use the owning contracts rather than reconstruct authority from UI state, a role label, OCR output or another module's mutable projection. See [business-access contracts](business-access-contracts.md), [historical reads](historical-reads.md), [person authority](person-authority.md) and [stock authority](stock-authority-contract.md).

## Release and runtime boundaries

The default `release1` profile exposes the supported catalog, branch-request, staff-decision and identity journey, plus catalog maintenance. Request acceptance has no stock reservation or financial effect. [Frontend release scope](../../frontend/src/lib/release-scope.ts) and [proxy](../../frontend/src/proxy.ts) restrict pages/API access; the [.NET release profile](../../backend/src/UnitToko.Api/ReleaseProfile.cs) independently limits endpoint composition. Navigation filtering never replaces backend authorization.

The preserved local pilot remains Release 1 on migration **78**, with synthetic identities and catalog data. Full-system migration **79**, the current invoice-picker work and other work in progress are not installed or production-accepted merely because their source exists. Their current evidence and remaining work belong in the ledger. The public Vercel frontend is a preview without accepted hosted business connections; local synthetic-provider journeys do not certify the real Auth0 tenant or production operations.

Explicit `NEXT_PUBLIC_UNIT_TOKO_RELEASE=full` uses `frontend/.next-full`; default/`release1` builds use `frontend/.next`. Full native browser rehearsals check the full build and start their Next child with that profile. The persistent pilot continues to use `.next`. Do not rebuild or delete output being served by the pilot. Serialize builds and type checks because Next still updates shared `next-env.d.ts` and TypeScript includes. See [pilot startup](../runbooks/local-pilot-release1.md) and [isolated browser rehearsal](../runbooks/stock-count-browser-rehearsal.md). Selecting `full` removes the pilot filter; it does not prove acceptance or retire legacy handlers.

Maintained browser requests use one public HTTPS origin with the approved forwarding/network boundary to the .NET API. The local pilot's HTTPS edge routes API/auth traffic directly; deployed Next rewrites require the approved API ingress. Production identity uses the Auth0/OIDC integration, verified email, fresh MFA where required, server-side sessions and scoped permission/person checks. Real tenant and host acceptance remain gates in [identity hosting](../runbooks/identity-hosting.md).

Private originals belong to the [evidence admission](../runbooks/private-evidence-admission.md) and [storage](../runbooks/private-evidence-storage.md) owners, not public assets or browser persistence. The selected OCR engine is one pinned local **Tesseract 5.5.3 / tesserocr 2.11.0** runtime with `ind+eng`. Its bounded preprocessing and exact original/pipeline provenance produce suggestions, never financial authority. Current inputs are PNG/JPEG; PDF and delivery-document OCR remain pending. Worker registration requires the actual consumer/store and approved current processing policy; engine selection alone is not host approval. See [document processing](../runbooks/document-processing.md).

## Legacy boundary that still remains

Legacy runtime and build retirement is **unfinished**. Retained Next handlers such as [`/api/state`](../../frontend/src/app/api/state/route.ts) and [`/api/commands`](../../frontend/src/app/api/commands/route.ts) import `@legacy/server` and legacy domain code. [Legacy page-session helpers](../../frontend/src/lib/server/page-session.ts) also remain. The old [Workspace](../../frontend/src/components/workspace.tsx) and [operations](../../frontend/src/components/operations.tsx) still contain legacy calls, although the maintained `/workspace` entry now redirects to current identity/workspace discovery. Removing disconnected dialogs does not remove these handlers, their dependencies or every legacy caller.

Retained `frontend/src/lib/domain` view helpers mirror legacy types and read-only arithmetic for those old consumers. They are not a second command or authorization implementation: frontend selectors do not provide `scopeState`, `allowed`, `ownDivision`, `canReadAttachment` or `attachmentContext`; buyer helpers do not provide `assertBuyerAccess` or `buyerRefForActor`. Those legacy authority functions remain server-owned until the corresponding adapter is retired.

The `@` alias points to `frontend/src`; `@legacy` resolves to `backend/legacy` for retained server adapters. Neither is an external API contract. Browser modules, components, hooks and view/client code must not import legacy or server-only code, including transitively or through re-exports. [check-boundaries.mjs](../../frontend/scripts/check-boundaries.mjs), invoked by frontend lint, enforces this boundary.

The legacy package still has its own runtime dependencies. [Next configuration](../../frontend/next.config.ts) includes legacy SQL/native assets in server traces, externalizes `@libsql/client` and rejects mismatched frontend/legacy `@libsql/client` or `libsql` lock versions. [Vercel installation](../../frontend/vercel.json) still installs both packages. Do not delete dependencies, SQL history, assets or tests solely because a UI entry has moved. Retirement requires checked callers, verified maintained replacement behavior and preserved unmatched obligations. Real data conversion and one-writer cutover remain governed by the [production acceptance gates](../quality/production-acceptance.md).

## Test ownership and operating guidance

| Kind | Current owner |
| --- | --- |
| Maintained UI contracts, source bindings, permissions, forms and recovery | [frontend/tests](../../frontend/tests/), with actual browser drivers in [frontend/scripts](../../frontend/scripts/) |
| C# domain, authority, transactional integrity, migrations and HTTP | [backend/tests/UnitToko.Tests](../../backend/tests/UnitToko.Tests/); native browser cases connect a production Next build to the real local API and isolated MongoDB |
| Retained legacy view/domain/HTTP/SQL regressions | Existing versioned cases in `frontend/tests`, still run against retained legacy owners where applicable |
| Legacy golden replay | [legacy-golden.test.ts](../../backend/tests/legacy-golden.test.ts) and [legacy-scenarios.json](../../backend/tests/Fixtures/legacy-scenarios.json), invoked by [test-domain.mjs](../../frontend/scripts/test-domain.mjs) after baseline and future-date checks |

Keep frontend contract/view tests and backend owner/transaction tests aligned as replacements are connected. Legacy replay evidence is not proof of C# parity or hosted acceptance. Focused checks accompany changes; the preserved [Release validation workflow](../../.github/workflows/release-validation.yml) is the integrated release gate, subject to actual required repository checks.

Use [local development](../runbooks/local-development.md) for dependencies and contract generation, [the pilot runbook](../runbooks/local-pilot-release1.md) for persistent synthetic access, and [Release 1 deployment](../runbooks/release1-deployment.md) for external inputs. Publication of GitHub source or a Vercel frontend does not establish a working hosted API/worker/Mongo/Auth0/private-storage deployment, restore capability or business acceptance.
