# Release 1 deployment prerequisites

The [release checklist](../releases/release-1.md) is the acceptance record. A frontend deployment alone is not a working hosted pilot.

The application keeps Next.js/TypeScript, .NET 10, MongoDB and Auth0. Release 1 never writes stock reservations, payments or invoices. Private financial evidence remains in its existing architecture and is not exposed by this release.

## Required external inputs

1. An existing authorized .NET host with persistent encrypted identity keys, approved TLS/ingress and restart operations. Its `Release__Profile` must be `release1`.
2. An authorized MongoDB replica-set URI and dedicated database, credentials in provider secret storage. Apply the compiled migration worker explicitly before startup; preserve a backup and one writer during deployment. The separate local synthetic database must never be migrated into production.
3. An Auth0 confidential application/database connection: reviewed issuer, client ID/secret, connection ID/name, controlled claims namespace and installed assurance Actions. Configure the exact public callback `/auth/callback` and sign-out callback `/auth/signed-out`; validate verified email, MFA, revocation and secure approved-user provisioning against the real tenant.
4. Approved branch/business records, stable provider subjects and requester/staff assignments, plus the approved catalog. Email text alone is not an identity binding. Synthetic local identities and products are not acceptable production inputs.
5. Vercel `unit-toko-bni`, project root `frontend`, Node 24. `NEXT_PUBLIC_UNIT_TOKO_RELEASE=release1`; set `UNIT_TOKO_API_ORIGIN` only to the approved HTTPS API ingress. Remove obsolete demo secrets after checking that no retained deployment uses them.

## Routing and verification

Follow [identity-hosting.md](identity-hosting.md): one public HTTPS origin, sanitized forwarded headers, an exact directly connected trusted proxy and backend network isolation. A generic external rewrite does not prove that this network boundary is satisfied. The actual Vercel/API topology must pass origin, cookie, callback and spoofed-forwarding checks before admitting real accounts.

After deploying the pinned GitHub commit, verify the requester submission, staff decision and requester history in the real browser against the hosted API and MongoDB. Check refresh/retry and application restart, a second branch's denial, mobile layout, catalog edits, API/host logs and readiness. Record the deployed frontend and API versions, database migration version and measured outcomes in the release checklist. Do not substitute local fixture results for hosted acceptance.

### Concrete single-origin staging gateway

`templates/Caddyfile.template` assumes one direct TLS connection from the browser to the Windows host, an existing approved PEM certificate/private key, and Kestrel bound exactly to `http://127.0.0.1:5080`. It is not a template for Cloudflare, Azure Front Door, a load balancer or a second proxy. Only `127.0.0.1` is configured as the directly connected API proxy. Public port 5080 and any API bypass remain denied by the host/network controls.

The `/api/v1` and `/auth` segment routes preserve the full path/query, method, request body, `Origin`, CSRF headers, cookies and returned `Set-Cookie`/`Location`. They replace supplied forwarding/original headers with one client-IP/HTTPS/canonical-host hop. Operational `/health` and `/openapi` are withheld publicly. The remaining routes proxy pages and assets through verified HTTPS/SNI to the supplied Vercel deployment hostname, with its required upstream `Host`; only that frontend branch strips cookie/authorization/CSRF/actor/idempotency credentials and returned cookies. It performs no path-prefix stripping, caching or write retries. Caddy documents these [proxy/header semantics](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy) and [mutually exclusive handlers](https://caddyserver.com/docs/caddyfile/directives/handle).

Supply these together and verify them in the real providers; `gateway.json` records the expected binding rather than proving remote settings:

- A controlled canonical HTTPS origin, DNS, existing approved certificate/private key, funded Windows host/network and exact service identities.
- The verified same-commit Vercel HTTPS deployment hostname and actual access entitlement/protection. The gateway must reach it under the existing protection policy. If private origin access requires a provider-specific protected credential, that integration is a remaining choice; this template does not add a bypass token or disable deployment protection.
- Frontend `NEXT_PUBLIC_APP_URL` equals the canonical origin (`FrontendPublicOrigin`); `NEXT_PUBLIC_UNIT_TOKO_RELEASE` equals the explicitly chosen manifest profile (`FrontendProfile`); `UNIT_TOKO_API_ORIGIN` equals the same canonical ingress (`FrontendApiOrigin`). Rebuild the matching frontend when these build-time values change. Relative browser requests reach the gateway's direct .NET branch before the frontend. Direct `.vercel.app` access is not a second accepted login origin.
- API `Identity:Auth0:PublicOrigin` is the same origin. The actual Auth0 application must list exactly its `/auth/callback` callback and `/auth/signed-out` logout callback and the reviewed connection/Actions/assurance settings. Provider access, account tier and real user provisioning remain unverified.
- An operator-verified Windows x64 Caddy binary, exact version (template requires at least 2.11.0), reviewed signature/source and SHA-256. No gateway binary is downloaded or trusted merely because a hash can be calculated.

After those inputs are available, the operator can perform the separate pinned-binary check and `caddy validate --config <rendered-file> --adapter caddyfile` before any listener is started. Capture only exit status/safe code, not adapted JSON, paths, environment or certificate contents. Validation loads configuration/certificates but does not start the server; it does not prove upstream reachability or browser behavior. See the [official validation contract](https://caddyserver.com/docs/command-line#caddy-validate). The actual renderer passed an offline synthetic check using official checksum-verified [Caddy2.11.7](https://github.com/caddyserver/caddy/releases/tag/v2.11.7), exit0, with three nonfatal warnings retained.
