# Shipment preparation upgrade

Migration 23 adds `shipmentPreparations` and `shipmentPreparationVersions` after canonical order storage. It leaves applied migrations 1–22, orders, reservations, physical stock, generic shipments and money unchanged. A preparation is a shared versioned plan; this release does not dispatch, accept delivery or issue an invoice.

1. Select the reviewed release and approved target. Pause and drain every application, worker and integration writer. The migration lease coordinates deployers; it does not pause business transactions.
2. Verify a coordinated backup and restore rehearsal of the complete database, prior migration receipts, counters, order/decision/reservation/stock facts, authorization/session facts, catalog/prices, audits, command receipts and outbox. Preserve matching private evidence under its existing runbook.
3. Inspect both preparation collections and reverse preparation effect references. No earlier production preparation writer was approved. Any existing preparation records or matching audit/receipt/outbox/movement effects stop preflight before target DDL. Preserve those records and use an explicitly reviewed conversion or approved separate data destination; never delete them or fabricate history to pass.
4. Run the existing worker migration entry point from `backend`: `dotnet run --project src/UnitToko.Worker -- --migrate`. Verify version 23 and unchanged earlier receipts. The new stores require strict validators, one head per store suborder and unique preparation/revision versions. Compatible stronger validators and safe non-exhausted counters are retained. API startup does not apply DDL.
5. In approved isolated staging, use genuine staged identities and order-admission inputs to accept an order, explicitly prepare part of it, recover a lost save response, revise the shared plan, and reject stale concurrent revisions. Revoke the picker or cancel the order and verify a stale save cannot win. Verify preparation does not alter stock or money. Current list/detail/recovery must exclude unrelated stores and buyers.

Preflight checks every target before DDL and rejects unsafe collection options, retention indexes, incompatible uniqueness and invalid/exhausted allocators. MongoDB DDL is not transactional: after interruption keep writers paused, preserve diagnostics, stop the former deployer and resume the same reviewed release when its lease is released or legitimately expired. Compatible empty partial installation resumes. Do not downgrade schema history for an older binary. Use a reviewed forward correction or coordinated restore of matching application and data.

Local migration and browser fixtures are scoped evidence, not staging acceptance. Live policies, source obligations, dispatch/delivery/invoice workflows, actual providers and hosting, restore, one-writer cutover and the branch pilot remain release gates. This runbook does not authorize a live data cutover.
