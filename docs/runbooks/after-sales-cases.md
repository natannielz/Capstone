# Finalized-sale complaints and independent return decisions (migrations 47–48)

Use the existing controlled migration command from the authoritative checkout. Before a real upgrade, quiesce case writers and preserve a verified backup under the release procedure. The migration lease serializes installers; it does not stop business writers. The API requires current storage and never installs it.

Migration 47 requires empty `afterSalesCases`, no prior case-request audit/receipt/outbox effects, and no unconverted Foundation `cases` records. Unsafe target collection options, TTL/partial or incompatible unique indexes and invalid allocator values block before target DDL. Existing stronger validators and safe allocator values remain intact. Strict immutable format-1 storage and full requested-actor/key uniqueness are installed; an interrupted empty installation can resume. Applied versions 1–46 stay unchanged. Do not delete real historical cases or fabricate source/receipts to pass preflight; conversion and restore must preserve their provenance.

`/fulfillment/cases` uses `case.request` for source preview, submission and original-actor/key recovery, and `case.read` for list/detail. Neither permission supplies return approval or financial powers. Each reported receipt/SKU must exist on the exact finalized invoice, with positive base units at most the accepted quantity and the shared one-million line limit. Original packaging and quantities remain visible. Scope filters apply to every constituent before pagination; current authority and source fences apply at completion.

The immutable request, metadata outbox, operation receipt and audit commit atomically. Case reads revalidate original invoice/allocation/journal, receipt, shipment and order provenance. Recovery looks up the same actor/key, verifies the complete effect graph and never resends or closes an uncertain request. Client storage contains only recovery metadata. The protected projection excludes price, bank, person/grant and internal accounting records. Original sale/stock/journal business values remain unchanged.

Intake state is **requested / Menunggu pemeriksaan**. A scoped `case.manage` holder with current verified person evidence, distinct from the original requester, can manually authorize bounded goods for return inspection or reject the complaint. Five-minute fresh MFA is required for decision preview, recording, replay and recovery. The complaints desk uses separately granted `case.read` to open the report and `case.manage` to decide; neither supplies stock or financial powers. Customer explanations remain separate from private reviewer notes. Version-2 decisions preserve the original version-1 request and finalized invoice.

Migration 48 installs empty immutable `afterSalesCaseDecisions` and the Invoice owner's separate `invoiceCaseReturnFences`, without changing the accounting posting counter. It validates populated version-47 requests, their exact audit/receipt/outbox graph and canonical invoice anchors before target DDL; protected runtime reads retain the complete original business provenance checks. Unsafe target options, TTL/partial/incompatible unique indexes and orphan decision effects block installation. Stronger operator validators, safe indexes and applied versions 1–47 stay unchanged. Quiesce case writers for upgrade/restore; interrupted empty installation can resume. Never delete existing decisions to rerun an empty-target installer.

One decision, private audit, original-person approval receipt and metadata outbox commit atomically. The shared Invoice-owned fence serializes competing cases while the owner verifies their immutable histories and remaining accepted base quantities. Authorized returns across cases cannot exceed the original accepted receipt/SKU quantity. Same-key replay preserves the original participants and checks their current person authority and the caller's scope/session/MFA again. Recovery validates the original case/actor/key and never resends, closes or treats damaged/orphan history as zero capacity. Browser storage contains recovery metadata only.

**return_authorized / Pengembalian diizinkan untuk pemeriksaan** is permission to bring those goods for inspection. Physical receipt/condition inspection and quarantine, disposition/replacement, credit approval, independently approved payout recording and different-person verification still need their connected owner workflows. An authorized return does not restock goods, reduce the invoice, approve a credit or execute a bank transfer. Before live activation, the operator must accept the applicable customer return/refund policy and manual decision procedure; this local slice supplies no automatic entitlement. Case notifications remain queued until their real owning processor is implemented; the existing payment-notice processor does not process them.

The connected local harness uses actual Next.js, .NET and MongoDB with synthetic approved policies, people and sessions. It is not provider/business acceptance.
