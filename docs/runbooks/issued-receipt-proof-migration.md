# Receipt proof storage upgrade

Migration 27 installs `issuedReceiptProofs`. Migrations 1–26, accepted shipments, recipient receipts, original Surat Jalan bytes and private uploaded evidence remain unchanged. Generated proof documents use the existing Documents store with a distinct kind, operation and unique source key. This upgrade does not validate quarantined uploads or create historical proof copies.

Use the existing controlled worker migration entry point during an approved deployment with business writers quiesced. Preflight rejects any unaccepted proof rows or reverse audit/receipt/outbox effects, unsafe retention/index options and invalid/exhausted counters before installing the collection. Compatible stronger validation and safe counters are retained. The migration lease permits interrupted empty installation to resume; it does not replace operator control of business writers. Do not erase conflicting history or add a completion marker manually.

Only an authenticated original recipient with current receipt authority, or scoped preparation staff, can deliberately issue a proof from an accepted receipt. The command includes the expected receipt ID. Recipient downloads require the original recipient and current scope/person/session checks; shipment readers use current shipment scope. Issuance, audit, command receipt and outbox commit together. Missing or damaged accepted history cannot be repaired by another request key. Lost responses recover through the original account and operation key without reissuing.

The retained printable HTML contains consent, frozen product/package facts, exact accepted/rejected/missing quantities, discrepancy text, recorded time and Surat Jalan version/hash. Proofs have a separate 2 MiB bound to accommodate 100 lines with fully encoded discrepancy notes; the existing Surat Jalan limit stays 512 KiB. The API returns the stored bytes with private attachment headers; the client verifies length and hash before download. It is an electronic consent record, not certified electronic signing. Uploaded photos, drawn signatures, invoices and bank evidence are separate workflows.

Restore this collection together with shipment/receipt/document history, audits, command receipts, counters and outbox. Keep workers and external integrations paused until restored receipts and external acknowledgements are reconciled. Confirm that the same original bytes are available only to currently authorized accounts, corrupt history fails closed, and an existing operation cannot generate a second proof. Local fixture evidence does not accept live storage, recovery objectives, migration, one-writer cutover or the branch pilot.
