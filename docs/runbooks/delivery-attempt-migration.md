# Delivery attempt and QR revocation upgrade

Migration 28 installs `deliveryAttempts` and `receiptChallengeRevocations`. Applied migrations 1–27, original shipment receipts, QR records and issued documents remain unchanged. The upgrade does not invent historical visits or alter PIN failure counters. Upgrade the API only after this migration succeeds; receipt operations intentionally require the new storage safeguards.

Use the existing controlled worker migration entry point during an approved deployment with business writers quiesced. Both collections, related audit/operation/outbox effects, validators, indexes and the attempt allocator are checked before collection changes. Unexpected data, retention, filtered/hidden indexes, conflicting uniqueness or exhausted counters stop the upgrade. Compatible stronger validators and safe counters survive. The deployment lease records an interrupted or rejected step as applying; do not erase this record or manually mark it complete. Correct an operator-reviewed conflict or resume a safe interrupted empty installation through the migration runner.

Only the assigned courier with current `delivery.attempt` authority can append a failed visit. The reviewed command includes the prior sequence, explicit outcome, actual Jakarta visit time and explanation. The server checks the dispatch boundary, current time and previous visit time. Accepted history, audit, operation receipt, outbox and revocations of outstanding unconsumed QR challenges commit in one transaction. An original-key retry recovers the original visit; it cannot add a second visit. Loss of current membership or session authority aborts the transaction. Readers require current shipment scope; original request recovery uses the command permission, independently of shipment-list permission.

A failed visit revokes outstanding QR challenges. It does not record recipient acceptance, return physical goods, release stock, post money or cancel an invoice. A later visit requires a fresh recipient-bound QR. A race between failure and acceptance must produce one compatible result; an accepted receipt prevents new failed-visit reports. Separate revocation history leaves actual invalid-token counters accurate. A missing or altered visit, revocation or accepted operation must fail closed, including when issuing another QR.

Restore both collections together with shipments, receipts, challenges, issued documents, audits, operation receipts, counters and outbox. Quiesce writers and keep workers/external integrations paused until restored effects and external acknowledgements are reconciled. Verify original-key recovery, history continuity, a revoked old QR, fresh-QR receipt, current authorization and unchanged stock/money effects on the restored candidate. Rolling back to code that ignores revocations is unsafe after the first visit is recorded; retain compatible receipt enforcement or perform a reviewed coordinated restore with one writer. Never drop the new history to reopen a QR.

Local rehearsal uses isolated synthetic accounts and approved source fixtures. It does not accept live Auth0, hosting, provider storage, migration/restore objectives, operating policies, cutover or the branch pilot. Those remain release gates in the production progress ledger.
