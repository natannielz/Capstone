# Canonical order storage upgrade

Migration 22 installs `orders`, `orderSuborders`, `reservations` and `orderDecisions` after private drafts. It preserves migration receipts 1–21 and does not activate ordering policy, tax, credit, source control or production traffic. The public service still requires actual approved admission producers. Local browser fixtures supply explicitly synthetic inputs.

1. Select the reviewed release, approved target and service credentials. Pause and drain every application, worker and integration writer. The deployment lease coordinates migration runners; it does not pause business transactions.
2. Verify a coordinated backup and restore rehearsal covering the complete database, migration history, counters, stock/lot/source records, authorization/person/session facts, catalog/prices, drafts, orders, audits, receipts and outbox. Preserve private evidence with its matching metadata under the separate evidence runbook.
3. Inspect existing `orders` and `reservations`. The earlier Foundation migration created generic collections, but no canonical production order writer was approved before version 22. This migration requires all four target stores to be empty. Existing legacy records, unaccepted fixture records or orphan order audit/receipt/outbox/stock effects stop preflight before target DDL. Preserve them and prepare an explicitly reviewed conversion or separate approved data destination; do not delete, rename, fabricate history or reinterpret them to make the migration succeed.
4. Use the existing worker migration entry point from `backend`: `dotnet run --project src/UnitToko.Worker -- --migrate`. API startup does not apply DDL. Confirm all earlier receipts are unchanged, version 22 is applied, and strict validators plus reservation/order-decision uniqueness and scoped query indexes are installed. Compatible stronger validators and non-exhausted counters are retained; a retained stronger constraint may still require operator review before a valid order can be admitted.
5. In the approved isolated staging environment, verify the full buyer→independent branch review→store decision journey using genuine staged policy/source producers. Verify mixed store rejection and buyer cancellation, exact reservation conservation, no physical-stock change from release, denial outside assigned scope, stale review rejection and original receipt recovery after a lost response. A source archive, a test fixture or a migration receipt is not that acceptance.

Preflight checks every target and reverse order effect reference before the first target collection/index change. Unsafe options, TTL/partial/hidden/sparse indexes, incompatible extra uniqueness, wrong required indexes and invalid/exhausted allocators stop the upgrade. Command uniqueness remains enforced by the shared actor/operation/key receipt constraint; order-decision revisions and order/balance reservations have their own unique indexes. No business record, counter, stock quantity or cash balance is written by the migration.

MongoDB DDL is not transactional. If installation stops, keep writers paused, preserve diagnostics, stop the old runner and retry the same reviewed release once its lease has been released or legitimately expired. Compatible empty partial DDL resumes. Never overlap deployment processes, edit an applied receipt or downgrade the schema to satisfy an old binary. Roll back only through a reviewed forward correction or coordinated restore of the matching application and complete data backup.

The local source test suite now uses a separate `fixtureBusinessRecords` collection for generic transaction and permission probes. Historical generic metadata tests explicitly use the real version-21 predecessor chain. Current ordering tests use the actual version-22 migration and do not install their own order validators. Private evidence tests can set `UNITTOKO_EVIDENCE_TEST_PARENT` to an existing absolute protected directory for synthetic files; the real leaf and ancestor ACL checks still apply. Source/builds remain in the authoritative checkout.

## Scoped spending-rule governance

The spending-rule workspace is `/ordering/spending-policies`. Its implementation and current verification status are tracked in the [production ledger](../quality/production-progress.md). It selects an actual approved branch or division profile and retains the exact hierarchy/profile and policy versions reviewed by the proposer. Defining a rule uses the separate `order.spending.policy.read`, `order.spending.policy.propose` and `order.spending.policy.approve` capabilities; these are not granted by an existing role template or by individual-order `order.spend.approve`. Assign only explicitly approved scopes and their required branch/division or organization-wide relationship markers through the existing access-governance process. Proposal and decision commands require fresh MFA; approval requires an independently verified person distinct from the original proposer.

The proposer selects every-order approval, approval strictly above an explicit IDR threshold, or explicitly no per-order spending approval, with a beginning and end for validity. An order total equal to the threshold does not exceed it. A missing rule never means no approval is required. The reviewer examines the exact target, source/profile versions, rule and interval before approving or rejecting. A stale source/base version or expired interval cannot be approved; an authorized independent reviewer can reject a stale proposal. A future-dated latest approved rule is unavailable until its start; it does not silently fall back to an older rule. The current source becomes unavailable at expiry or after its governed source changes.

After a lost command response, use the original actor's operation lookup for `ordering.spending.policy.propose`, `.approve` or `.reject` with the original key. Do not infer success from a timeout or resend as a new operation. Immutable proposal/decision/version records, audit, receipt and outbox facts must agree; inconsistent history stays unavailable and must not be patched to manufacture approval.

Migration 59 adds the four empty `orderSpendingPolicy*` stores after approved postal sources. Use the same stopped-writer, verified-backup/restore and migration-runner protocol above. It does not seed a spending rule, threshold, grant, budget, credit limit or production approval. Actual D03 rule ownership, values, validity and supporting business decisions remain required. A spending-policy version supplies only that part of admission; full production order admission remains closed until commercial/tax, recipient/delivery, budget/credit and eligible stock/source obligations are genuinely connected and accepted. Store acceptance remains a separate decision.

No live upgrade or data cutover is authorized by this runbook alone.
