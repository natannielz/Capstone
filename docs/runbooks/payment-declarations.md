# Payment declarations and private original uploads

The connected M3 workflow records private buyer drafts, admits original bytes into quarantine, displays durable security-check results, and submits one eligible original for review. Submission records an exact evidence pin and an OCR request; it does not verify a payment, allocate cash, settle an invoice, approve a refund, or execute a transfer. Local OCR processing, independent bank [verification](payment-verification.md) and [allocation](payment-allocation.md) now have connected workflows; actual provider/business acceptance and remaining after-sales work stay open. Local fixtures do not accept any live provider, host, scanner policy, business policy or production data.

## Buyer workflow

`/billing/payments` requires both current `payment.evidence` and `invoice.read` permissions. The API checks every referenced invoice's actual constituent scopes and retained history. A draft can reference up to 20 distinct invoices belonging to the same buying organization, seller organization/shop and channel. Amounts remain checked decimal strings and BSON Decimal128; Int64 IDs and revisions remain strings across the HTTP boundary.

Only the original recorder can read, edit or recover a draft. Finance and technical administrators do not acquire access to these private drafts from their job titles. Changes append immutable versions with the original recorder, invoice snapshots, prior version/hash, request receipt and audit. Concurrent edits use the expected revision; the losing edit must reload. Missing or damaged prior history blocks reuse rather than recreating it.

Saving without a photo is permitted only while the record remains a draft. Each image reservation binds the payment declaration, current admitted revision, uploader and seller's storage scope. Scope/actor/session checks run again at durable upload transitions and after slow I/O. Uploading alone creates no payment-evidence association. Submission pins the exact declared-value version and eligible evidence reference/version/hash, then locks those values and that image. Later financial acceptance must satisfy the independent-maker and actual bank-review rules.

The screen accepts JPG/PNG originals up to 10 MiB. This client check is convenience only: the server treats all bytes as untrusted, imposes its own bounded stream, and applies the approved private-store policy's possibly smaller limit. A completed file is labelled as awaiting security checks. Filename, client MIME, a digest or a successful HTTP response never supplies a clean verdict.

Use **Pilih bukti pembayaran** for an existing image or **Ambil foto bukti pembayaran** for the device's rear-camera capture control. The browser may offer its normal file picker when camera capture is unavailable. The local preview appears before upload; **Putar tampilan 90°** changes its presentation only, preserving the original file bytes/hash. **Hapus pilihan berkas** releases the local preview. Selecting another file, opening another declaration or leaving the workspace releases the previous object URL. No local image or orientation is stored in the operation journal. This preview does not certify security eligibility or replace the later checked original read. The native indeterminate upload indicator covers the actual reserve/upload/result-check operation; it shows no invented percentage. An uncertain outcome still uses the original reservation and receipt lookup.

After security checks pass, the buyer deliberately chooses an image, reviews the amount, transfer date, payer, reference and invoices, then selects **Ajukan untuk verifikasi**. The server verifies the actual original outside the Mongo transaction and holds its protected handle. In the final transaction it rechecks current ownership/session/scope, declaration revision, original tuple, lifecycle, worker/read policies and bounded lease. The declaration association, Documents-owned pin and audit, command receipt, submission audit and `payment.ocr.requested` job commit together. A required audit/queue failure rolls everything back. Two submissions cannot create two associations for the same declaration.

The buyer then sees **Pengajuan tersimpan** and can view the selected original. Edits and new uploads for that declaration are denied. The scoped durable OCR worker can produce recorded suggestions, but pending/failure never implies successful extraction or payment approval. The original recorder/uploader account is retained, and `personAtSubmission` records current verified or explicitly unknown identity evidence. It does not fabricate a historical person snapshot for older draft/upload records. Unknown provenance cannot authorize a later financial approval. Finance's scoped original/correction/manual-exception/bank-verification work is described in the [verification runbook](payment-verification.md).

For a submitted declaration, **Muat tindak lanjut petugas** reads the actual immutable claim/release/rejection/replacement-request history. The API checks the original recorder's current payment/invoice authority, every constituent scope, exact declaration revision and submitted original tuple. The response includes only this declaration's follow-up state/version and timestamps. It never returns internal staff reasons, staff identities, bank facts, payer anchors or a financial-acceptance claim. The private read requires the reviewed actor, same-origin CSRF and exact revision, is audited and is fenced again before returning. Missing or inconsistent action history denies the read.

A rejection or replacement request closes fresh verification on that original submission; its declared values and image remain immutable and readable under current authority. The displayed follow-up is separate from bank verification, allocation and the actual invoice balance. Linked replacement creation, customer-specific explanations, delivered/failed notifications, supplements and remaining after-sales states still need their owning workflows. This read neither sends a notification nor creates a new image, declaration, refund or transfer.

Pins have no TTL. Future retention/cleanup must consult their owning association and serialize with the same lifecycle; no cleanup path is enabled by this release. A pin does not override later security revocation or expiry. Current viewing still requires valid security policies; aged-out verdict refresh and worker/reviewer access are separate unfinished work.

## Unknown results

Draft saves, reservation requests and submissions retain only actor, operation, original key and timestamp in the existing browser recovery journal. No image, transfer amount, payer information, reason or credential is written to that journal. Reservation/submission keys include the declaration ID as a recovery reference; this is not authorization. Recovery must still pass the owning API's current checks.

Use **Periksa hasil** after a lost save/reservation/submission response. An absent receipt remains unconfirmed and cannot be closed through the generic access-administration endpoint. The submission-specific adapter never falls back to draft recovery. A matching completed submission can be recovered without reopening bytes or queuing OCR twice; changed content under the same key conflicts. Do not resend a changed command under that key or create another reservation merely because a response was lost.

Once the reservation exists, read its durable status. A `fresh` attempt may receive the chosen original. `writing` and `publish_pending` require recovery of that attempt; pending publication can only use its committed exact byte tuple. Upload recovery never reads a new browser file. `interrupted` is incomplete and retains its quota charge. `quarantined` retains the immutable original and its validation request, with scanner/decoder explicitly unavailable. The buyer screen performs a read after uploading, so a lost upload response can be reconciled without another byte upload.

## Requested replacement

When the private follow-up says **Petugas meminta bukti pengganti**, use **Siapkan bukti pengganti**. The server reads the exact closed submission and immutable staff request. Confirmation creates one separate draft for that parent; if it already exists, preparation opens it. The original submission, original bytes, review history and invoice balance remain unchanged.

The replacement copies the original invoice group and transfer fields. Invoice selection is locked; review and correct the transfer fields, save, upload a new original, wait for security checks, then explicitly submit it. The replacement links back to **Buka pengajuan asli**. It has its own upload reservation, pin, submission and subsequent review. Creating/submitting it is neither bank acceptance nor allocation.

If creation loses its response, use **Periksa hasil** after reloading. The dedicated `billing.payment.replacement.create` adapter looks up the original `rp.<parentId>.<UUID>` key under current buyer authority. It cannot close an unconfirmed attempt or resend creation. The local journal retains only actor/operation/key/time. Missing source history, receipt, audit, metadata effect or current scope blocks recovery; operators must investigate rather than rebuild the history.

Migration 44 extends only the owning immutable draft-version schema and adds partial uniqueness on the parent of an initial replacement version. It preserves previous receipts, stronger conjunctive rules and actual predecessor histories. Unsafe indexes/options/counters, unexpected new versions or orphan replacement effects block installation before DDL. Empty interrupted DDL can resume. Stop application writers throughout DDL, rehearse restore and migration against the actual approved copy, and retain the one-writer cutover gate. Do not delete applied receipts to downgrade or adopt unverified rows.

Local synthetic browser/API/Mongo checks do not activate real storage, deliver notifications, authorize financial actions or establish staging/production acceptance.

## Explicit host configuration

The API defaults to unavailable private storage. Operators may supply `Evidence:PrivateWindows:Root`, `Evidence:PrivateWindows:StoreId` and `Evidence:PrivateWindows:TrustedOperatorSids` through the approved runtime configuration. Partial settings fail startup. The existing adapter validates the real local NTFS root, ancestors, ownership, ACLs and service rights. Unsupported hosts or unsafe permissions remain unavailable. Configuration does not seed quotas or mark the host production-accepted.

An approved, active `evidenceStorePolicies` record with finite content, capacity, timing and buffer limits is also required. No deployment/request handler creates it. Never put the root under public assets or version control, loosen an existing directory's permissions to make a check pass, or activate it on unaccepted production infrastructure. Follow [private storage](private-evidence-storage.md) and [admission operations](private-evidence-admission.md).

The new byte endpoint has matched endpoint metadata; only that route bypasses the 64 KiB JSON buffer. It still requires the authenticated session, exact origin, CSRF, expected actor and quoted revision. It accepts unencoded `application/octet-stream`; chunked bytes remain bounded. It exposes no private path, generation, claim token or download URL.
