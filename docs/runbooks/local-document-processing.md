# Local evidence decoding and scanner adapters

The M3 worker can now connect these adapters to exact original versions, immutable Mongo verdicts and scoped payment status. It remains **unconfigured by default** and cannot claim jobs without a current explicit worker approval and an active accepted storage policy. Uploads remain in private quarantine and payment drafts remain unsubmitted. A scan/decode result does not expose an original, grant evidence eligibility, run OCR or approve money. Controlled preview, exact eligible associations, local OCR and bank review remain separate work. Provider and host acceptance are separate from local adapter tests.

## Decoder

`UnitToko.ImageDecoder` is a separate .NET executable with a pinned Magick.NET-Q8-AnyCPU 14.17.2 dependency and a NuGet content-hash lock. The package's ImageMagick and bundled dependency notices accompany build/publish output. The parent checks SHA-256 for the explicit .NET executable, helper assembly, runtime/dependency configuration, both managed decoding assemblies, native Windows x64 library and policy, holding read locks for the invocation. Hashes must come from the reviewed release manifest, not an untrusted upload or a runtime self-approval step. Runtime framework/OS versions and protected installation directories still require acceptance.

The child receives only bounded original bytes on stdin and returns bounded JSON containing the result, dimensions, media type, actual byte count and SHA-256. No filenames, file paths, user identity, Mongo credential, financial fields or ordinary parent environment are passed to it. The parent recomputes the input hash/count and checks the returned tuple. Decoder error text is not logged or returned. Unconfigured, unsupported or mismatched installations remain unavailable before consuming bytes.

Windows job membership is assigned **at process creation**, with committed-memory, CPU-time, active-process and kill-on-close limits. The child independently checks the actual job limits before reading input. A separate wall deadline terminates the job and closes its pipes. Only the three intended pipe handles are inherited. No breakaway is enabled. The current adapter supports Windows x64 only; other hosts need their own enforced implementation and acceptance. A cancellation token alone is not the resource boundary.

Only JPEG and PNG containers reach the decoder. Container checks reject CRC errors, trailing/truncated containers, APNG and multi-picture JPEG envelopes; actual decoding reads all pixels and requires exactly one frame. Native warnings, including incomplete JPEG scan data despite an appended end marker, reject the image. Dimensions/pixels/bytes and native profile/memory limits are finite. Native module loading is enabled only for JPEG/PNG; coder rights allow reads only. Delegates, filters, path operations, disk and mapped pixel caches are denied. The native list budget is two to account for its internal collection slot; the accepted output still must contain exactly one frame.

**Resource confinement is not full security isolation.** The helper must run under an accepted restricted operating-system identity, with denied network egress, protected runtime/configuration and no access to application secrets or unrelated private files. The current job wrapper alone does not establish those properties. Do not activate processing merely because local decoding passes. No service-account change, firewall change, production binary installation or host approval has occurred.

## Local scanner protocol

`LocalClamdScanner` accepts only the explicit IPv4 loopback endpoint; it performs no DNS lookup, cloud request or file-path scan. It sends a bounded `INSTREAM` payload and accepts only the exact clean reply. Positive detections remain infected/ineligible; limit-exceeded, malformed, failed, missing, stale and timed-out results remain unavailable/ineligible. It checks the exact configured engine version, minimum definition version and bounded definition age before sending bytes and again after scanning. A version change during scanning invalidates that invocation. Its hash and length refer to the actual stream it sent.

Real activation requires an approved, supervised local ClamAV service with accepted engine/signatures, matching stream/scan/queue limits and UTC timestamps for the version response. The unauthenticated loopback protocol does not prove the listener's identity: host/service ownership and access controls must be demonstrated independently. Freshclam updates and any required outbound update access need their own approved operating configuration; this client neither installs nor updates a service. Current scanner tests use a clearly labelled loopback **protocol simulator**, not a real engine or a claim of malware-detection acceptance.

## Worker composition and operational inputs

Run schema migration explicitly before starting the API/worker release. Forward migration 32 creates `evidenceValidationPolicies`, `evidenceValidationResults` and `evidenceValidationAudits`, and extends only the evidence-kind outbox constraints. It preflights every target before DDL, rejects preexisting unaccepted validation records, preserves stronger validators and applied history, and resumes an empty interrupted installation. Do not insert worker policy rows before that migration is accepted. The worker checks the complete current migration history before each processing attempt; it does not migrate on normal startup.

The worker reads the optional `Evidence:Validation` configuration section. It requires `Root`, `StoreId`, `TrustedOperatorSids`, `ConsumerId`, `HostAcceptanceReference`, `Limits`, `Decoder` and `Scanner`. `Limits` supplies maximum bytes, width, height and pixels. The `Decoder` fields are the explicit executable/helper paths, eight reviewed SHA-256 pins, memory limit and timeout from `ImageDecoderOptions`; the `Scanner` fields are loopback port, exact engine, minimum definition version, maximum definition age, byte cap and timeout from `LocalClamdOptions`. The scanner byte cap must equal the image byte cap. No production defaults or fabricated approval row are supplied. Never place Mongo credentials, private content or runtime secrets in a committed configuration file.

`EvidenceValidationRuntime` constructs only the real Windows private store, bounded decoder and local ClamD adapter. It emits a pipeline fingerprint over the versioned configuration, limits and host acceptance reference. This identifies the configuration; it is **not approval**. After reviewing the actual host/release/service inputs, the authorized operator must provision the exact fingerprint in a current `evidenceValidationPolicies` record: Long ID, schema version 1, consumer/store/pipeline identities, active state, Long revision and fence, approval/expiry times and the recorded host acceptance reference. No UI or runtime path auto-approves this record. Policy revisions must change when authority changes; fences are for concurrent processing. Preserve audit of provisioning/revocation in the accepted deployment procedure. The application startup identity must not be permitted to grant itself this approval in the deployed Mongo roles.

Only `evidence.validation.requested` jobs are claimed. Each claim is bounded to five minutes and five attempts, with one-minute transient retry spacing. The processor rechecks the immutable admission/audit/receipt graph and storage generation, scans the verified original, reopens it for full decoding, then fences the current lease, processing policy and storage policy in the final transaction. Its immutable result, dedicated service audit and outbox processing receipt commit together before acknowledgment. A crash after commit recovers that same result without rescanning. A stale claim, policy revocation, damaged graph, unsafe/missing file or unavailable adapter cannot publish a clean result. The private file adapter retains exclusive read handles; a competing read is a transient failure, not permission to weaken the file boundary.

The result is a separate validation record. It does not rewrite immutable admission verdicts or move the original out of quarantine, and the worker writes no Billing or Accounting collections. Scoped status checks bind the result, service audit and queue receipt to the exact original, and withhold verdicts after approval expiry/revocation. The buyer sees pending, unsafe/unreadable, unavailable or security-check-complete text; every successful security check still states that the payment is unverified. This display is not the future submission/association eligibility check.

Worker logs report bounded operational statuses only, with no exception payloads, bank fields, file paths or content. Persistent dead jobs, missing approvals, schema mismatch and integrity failures need operator attention; automated alert routing remains M5 work. Real restricted service identity, Mongo permissions, installed binaries, firewall/network isolation, scanner ownership and definitions still need M6 acceptance. No real service or host approval is inferred from local tests.

## Local evidence and remaining work

Set `UNITTOKO_DECODER_DOTNET` to the approved absolute local .NET executable before running the Windows `ImageDecoderTests`; their helper is built/copied by the test project. `ImageDecoderAvailabilityTests` and `LocalScannerTests` also run on other hosts. Keep the Windows cases explicit in release validation; Ubuntu skips do not demonstrate them.

`tmp/production/payment-results/media-confinement-final.trx` exercises actual JPEG/PNG decoding, corrupt compressed PNG, CRC/truncation/trailing/animation rejection, an incomplete JPEG scan with an end marker, width/pixel/byte bounds, dependency mismatch before source read, actual job memory failure and stalled-input termination, plus scanner protocol failures and identity freshness. The earlier WIC prototype accepted corrupt compressed PNG; a subsequent Skia prototype accepted the truncated JPEG. Their failed evidence is retained. Neither prototype remains in source or was registered in production; the rejection assertions were retained.

The connected worker tests exercise real Mongo, private Windows files and the actual decoder. Scanner tests and browser fixtures use explicitly synthetic verdicts or a labelled loopback protocol simulator; neither is actual ClamAV acceptance. Only separately validated, currently authorized and transactionally pinned evidence can later support submission. Local OCR, independent bank review, controlled viewing/associations, money allocation and after-sales remain required.
