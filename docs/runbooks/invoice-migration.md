# Invoice issuance storage (migration 29)

Run from the authoritative checkout with the existing deployment migration command. Applied versions 1–28 are unchanged. Stop all invoice writers and preserve a verified backup before an actual upgrade. The migration lease coordinates deployers; it does not quiesce business writers. The API never installs storage.

Migration 29 requires empty `invoices` and `invoiceSourceAllocations`, no prior invoice balances, source journals, operation receipts, audit/outbox effects or invoice-number sequences. Historical invoice data is a conversion/restore gate. Do not delete it to pass preflight or invent receipts and prices. Existing stronger validators, allocator values and exact Foundation partial indexes are preserved. Full uniqueness is installed for seller/channel/year/number, issuer/request and accepted receipt/SKU allocation. Both collections and effects are preflighted before target DDL; interrupted empty installation can resume.

Invoice issuance consumes eligible immutable recipient acceptance and the original order's package, price and commercial versions. Earlier allocations are revalidated through Fulfillment and Ordering, including their signed-receipt history. Only accepted base units are billable. Cumulative rounding conserves the ordered amount across partial deliveries; total tax/charge allocation cannot exceed the original order. Receipt allocations, invoice number, private printable document, accounting journal, audit, operation receipt and outbox reference commit together. Failed accounting or final authorization leaves no issued invoice or consumed receipt.

An invoice can cover multiple receipts only under an approved grouping rule and a common buyer/seller/channel. Every constituent scope must be authorized before list pagination, detail or download. Issuance recovery belongs to the original actor and request key, requires current authority and never resubmits or closes an unknown operation. Previously issued documents use frozen content; private attachment downloads validate the content hash. Payment status must come from the future verified allocation/credit owners, not an assumed zero balance.

Production composition deliberately has no `IInvoiceAdmissionReader` until the actual owner-backed, independently approved grouping, period, tax allocation, payment term/calendar, numbering, seller/template and account mapping inputs exist. The adapter must conditionally write its source within the same transaction and verify it again at completion. Local test policy, a 30-day example, approved chart fixtures and fixture profiles are not business approval. This invoice document is not a substitute for an official tax document.

Actual restore rehearsal, numbering continuity against real records, live tax/accounting policies, provider delivery/notification behavior, one-writer cutover and branch pilot acceptance remain release gates. M6 must verify the exact hosted frontend/API/worker/Mongo/Auth0/private-storage release; publishing source alone is not acceptance.
