# Bounded outbox consumers

The durable queue requires an explicit server-side consumer policy: an immutable list of 1–32 exact event kinds, a maximum of 1–1,000 delivery attempts, a lease of 1 second–1 hour and a fixed processing interval no shorter than the lease and no longer than 1 hour. These are accepted configuration bounds, not selected production values. There is no unrestricted claim overload. Validation, payment OCR and the private payment-notice worker are separately registered and explicitly configured; registration does not supply production host or business acceptance.

A claim atomically selects a due pending/retry event or an expired lease of an allowed kind. It stores the lower of its prior attempt limit and the configured limit, then either issues a new owner/token or marks exhausted work dead. Increasing a later consumer policy does not silently resurrect the event or expand its stored retry budget. Lowering the policy applies when the event is next claimable. A claim call terminalizes at most 16 exhausted candidates, then yields; a null result can mean more work remains for the next poll.

A soft lease may be reclaimed after expiry while attempts and the processing deadline permit. An expired hard processing deadline is terminal. Renewal uses the stored deadline, cannot shorten the existing lease and cannot extend the hard interval. Stale tokens, the wrong owner/kind, expired leases and expired processing intervals cannot renew, complete or retry. The final permitted attempt can complete successfully; another retry becomes dead.

Failures store only a fixed safe reason code. A permanent failure is terminal; a transient failure schedules an explicitly bounded retry delay of up to one day, subject to the stored attempt limit. Normal logs and queue metadata must not contain raw OCR, account details, bytes or exception text. Queue state writes explicitly use majority write concern even when a client has weaker defaults. Unknown database outcomes propagate; a caller must not assume the claim or acknowledgement failed.

A claim is work coordination, not application authorization or proof of a valid document. The future validation worker must recheck its exact evidence generation and processing claim, enforce actual process time/memory/egress limits, and persist an idempotent validation result before acknowledging the event. A repeated delivery after a crash must read that result and avoid a second business effect. Completion of the outbox row alone does not mark evidence clean or funds received.

The existing process-kill test still proves at-least-once delivery: kill after a simulated downstream acknowledgement, restart after soft lease expiry, deliver again and record exactly one downstream effect. This is a test service, not a real integration or exactly-once transport claim.

Remaining production work includes other module/channel processors, kind-specific service credentials, accepted bounded hosts, alerts for dead/overdue jobs and an audited operator recovery workflow. No automatic reset of attempts, dead-event replay, deletion or retention policy is supplied.

## Private payment notices

Migration 45 extends the existing outbox with a strict notification-receipt constraint. It preserves prior receipt/history, other kinds and stronger operator rules. Preflight refuses unsafe options/indexes, orphan source actions, unexplained prior consumption and unaccepted receipts before DDL. Empty or populated interrupted installation can resume. Quiesce all application writers for the entire upgrade, capture the approved backup and prove restore, then apply the explicit migration and verify its completion. The migration lease does not quiesce API/worker processes. No applied receipt is deleted or downgraded in real operations.

After approved host/database activation, `Notifications:PaymentReviewInApp:Enabled=true` registers the actual .NET payment-notice worker. It defaults to disabled; migration mode never claims jobs. The worker must see a completed current migration and the required strict outbox storage before claiming. It consumes only `billing.payment.review.manage`, using consumer `payment-review-in-app-v1`, five attempts, a 30-second lease and two-minute processing budget. Validate those bounds against the actual workload and host clock during release acceptance. The full source-history check has a documented large-history ceiling; release load checks remain required.

The worker validates the owning submitted declaration, original recorder, exact immutable action/source and command/audit/producer graph. It atomically completes that event with a source-bound receipt under its exact current token/attempt/budget. Rejection/replacement makes a controlled in-app follow-up notice available to the original account's private payment reader. Claim/release events record `not_applicable`, with no customer notice. Current buyer ownership and every constituent permission/scope are still required to read; receipt availability never grants access. Internal staff reasons, original bytes, account contacts and bank information are not copied to the notice.

Pending/running/retry/failed status comes from the actual event. Availability requires the exact receipt, including source hash, recipient, disposition, bounded claim provenance and completion time. Generic outbox completion cannot supply it. Original-token recovery validates the same durable result; another claim cannot duplicate it. An uncertain commit propagates and is never rewritten as failed. Corrupted history denies the reader. A failed event retains its bounded reason/attempt metadata for operator investigation; this release supplies no dead-letter replay or automatic attempt reset.

This worker supplies private in-app availability only. It sends no email, SMS, WhatsApp, bank command or other external message; the receipt is neither a read acknowledgement nor payment acceptance. Other channels, invoice/document processors, escalation and customer-specific public explanations remain required. Local real-worker/browser fixtures use isolated Mongo and synthetic operational inputs; actual deployed worker/provider/restore/pilot acceptance is still pending.
