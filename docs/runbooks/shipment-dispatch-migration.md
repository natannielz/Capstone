# Shipment dispatch upgrade

Migration 24 installs canonical immutable dispatch records in `shipments`, after the order and preparation stores. Applied migrations 1–23 remain unchanged. A dispatch consumes selected reserved packages through Ordering and Inventory in one transaction; it does not prove recipient acceptance, create an invoice or post money.

1. Select the reviewed release and approved target. Pause and drain all application, worker and integration writers. The migration lease coordinates deployers; it does not suspend business transactions.
2. Verify a coordinated database backup and restore rehearsal, including migration receipts, counters, orders/decisions/reservations, preparation versions, stock movements/balances, identities/access, audits, command receipts and outbox. Preserve matching private evidence under its existing runbook.
3. Inspect `shipments`, reverse dispatch audit/receipt/outbox/movement references and `shipment-number.*` counters. There was no earlier approved canonical dispatch writer. Existing shipment data, orphan effects or document-number counters stop preflight before target DDL. Preserve the data for a reviewed conversion or approved separate destination; do not delete it or fabricate accepted history. A safe existing internal shipment ID counter may be preserved; it is not the document sequence.
4. Run the existing worker migration entry point from `backend`: `dotnet run --project src/UnitToko.Worker -- --migrate`. Verify version 24 and unchanged earlier receipts. The strict shipment schema binds the original preparation/source, exact selected reservations/lots, courier snapshot, approved source/cost references, stock effects, audit/receipt and document number. Unique keys enforce order dispatch sequence and seller/channel/Jakarta-year document sequence. The compatible original partial number index is retained alongside the full canonical uniqueness rule; unsafe indexes and retention options are refused. API startup does not perform DDL.
5. Install and accept genuine source/cost admission producers before enabling live dispatch. The public service deliberately has no permissive fallback. Local synthetic readers are not production adapters, approved costing policy or source-obligation reconciliation. Assign `shipment.dispatch` and `shipment.assign` explicitly for this combined workflow; selecting a courier requires that courier's current scoped `shipment.read` and `delivery.attempt` grants and approved assignment membership. Do not widen a role template merely to make the screen appear.
6. In approved isolated staging, prepare part of a real staged accepted order, deliberately choose its physical lot and eligible courier, review and dispatch. Verify exact reservation and physical-stock reductions, unchanged commercial/package snapshots, one immutable shipment, one original command receipt and the scoped document number. Recover a lost response without dispatching again. Exercise competing dispatches, cancellation of the remaining quantity, stale stock/courier/source authority and revocation. Verify unrelated stores and users cannot read the queue, courier choices, detail or recovery.

All preflight targets are checked before DDL. MongoDB DDL is not transactional: after interruption keep writers paused, preserve diagnostics, stop the former deployer and resume the same reviewed release when its lease is released or legitimately expired. Compatible empty partial installation resumes. Stronger compatible validators, prior history and safe counters are retained. Do not downgrade migration history for an old binary; use a reviewed forward correction or coordinated restore of matching code and data.

Shipment numbers are allocated inside the dispatch transaction, separately from internal IDs, by seller/channel/Jakarta year. Failed dispatches issue no document number. A number alone is not an issued PDF, recipient proof or invoice. Delivery attempts, recipient-bound QR/tablet consent, document rendering, invoice eligibility, real providers, full release validation, restore, one-writer cutover and the branch pilot remain release gates. This runbook does not authorize real data cutover.
