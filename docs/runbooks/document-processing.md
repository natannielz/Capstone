# Local document processing

## Current boundary

The selected local engine is **Tesseract 5.5.3 / tesserocr 2.11.0**, using the pinned `tessdata_fast` Indonesian and English models together (`ind+eng`). [The asset manifest](../../backend/document-processing/tesseract-candidate.json) fixes the wrapper/model versions, checksums and notices. This selection does not approve a production host, processing policy or accuracy threshold; no competing-engine selection is required. The internal `ILocalOcrEngine` accepts one assigned image stream and returns bounded suggestions with source locations, confidence and exact model/runtime/preprocessing provenance. The backend remains .NET; the isolated Python/native helper has no application API, Mongo credentials or financial operations.

The worker registers payment processing through optional `Evidence:PaymentOcr` configuration and supplier invoice/SPH processing through `Evidence:SupplierDocumentOcr`. Both use the same pinned engine with their own purpose-specific parser, pipeline identity, consumer and approved policy. Missing configuration/current approval leaves the corresponding processor unavailable. Migration 35 supplies payment processing grants/results/failures/audits; the separately migrated [supplier-document owner](supplier-documents.md) supplies its own immutable submission and result graph. The payment workspace displays queued/running/retry/dead/succeeded status and exact-source suggestions; Finance has separately permissioned viewing and correction. OCR never changes entered facts, verifies funds, approves a match or posts money/stock.

**Supported inputs today are eligible single-image PNG and JPEG originals only.** Existing security admission, clean scan/full decoding, configured byte/pixel/dimension limits and exact private ownership remain mandatory. PDF/multipage processing and a delivery-document extraction owner are pending; neither is enabled by choosing this engine. Never reinterpret them as payment or supplier-image input.

The adapter checks exact helper/runtime/library/model pins, retains read locks, uses isolated Python startup, and binds output to the actual stream SHA-256 and requested immutable evidence reference. It bounds bytes, pixels, text, fields, coordinates, JSON/output size, child count, memory and elapsed time. Memory/process confinement is not an egress firewall or a restricted service identity. Production activation needs approved immutable directories, runtime/standard-library/dependency review, denied network egress and separately restricted worker credentials.

Unknown fields stay null. Amounts use strict IDR grammar and the existing money bounds; the parser never repairs `O` to `0`, treats balance/fees as transfer amount, resolves conflicting labels, fills a missing date, infers timezone or confirms that funds arrived. Confidence is engine output, not probability of a payment. A human must compare the original, suggestions, entered facts and actual source/bank records. An unreadable image or unresolved orientation calls for re-upload or an explicitly authorized manual-review route; quarantine/security failures have no OCR bypass. Boundary-contact and low-confidence flags are limited observations, not a complete blur, clipping or duplicate-image detector.

## Bounded v2 preprocessing and provenance

The current image pipeline is `bounded-gray-orient4-deskew10-contrast1-psm6-ind+eng-v2`. The persisted preprocessing identity appends `payment-labels-id-en-v1` or `supplier-document-labels-id-en-v1` for the owning parser. It converts a working copy to grayscale, applies bounded contrast adjustment and compares four fixed quarter-turn orientations using the same engine; it does not download an orientation model. The projection-based skew search is bounded to ±10 degrees and finite sample/angle counts. Working-image scaling and rotation expansion also have hard pixel/edge limits; transformed copies do not replace the original.

Weak/ambiguous orientation, absent text or out-of-range skew yields no inferred text/fields. Field locations are inverse-mapped and normalized to the **original** image, whose hash and dimensions remain checked. Detailed orientation/skew/contrast diagnostics are bounded private helper/measurement output, not reviewed business facts. Immutable extraction provenance binds the engine, model version/checksum, runtime checksum and image/parser versions. Changing helper/runtime/model bytes or preprocessing requires a newly derived pipeline identity and matching reviewed policy; do not relabel historical v1 results or reuse an old approval for changed code.

## Worker and private result boundary

`PaymentOcrRuntimeOptions` and `SupplierDocumentOcrRuntimeOptions` require the private root/store and trusted operator SIDs, a dedicated consumer ID, approved host and selected-model release references, explicit engine paths/limits and reviewed SHA-256 pins. The configuration field remains named `ModelSelectionReference`; it identifies the approved selected-engine release, not permission to switch engines. The runtime does not derive approval pins from installed files, seed policies, run migrations or download models. Independently verify the exact compiled runtime's `PipelineId` against its reviewed helper/runtime/model/parser manifest, then provision the corresponding finite approval for the **actual consumer and store**. Payment matches `documentProcessingPolicies`; supplier processing matches its own `supplierDocumentProcessingPolicies`. Both require the exact pipeline, host/model approval references, active policy revision and expiry; an arbitrary reference string is not host acceptance.

The production default remains unconfigured. Run the complete current schema chain explicitly with writers quiesced, preserving backups and migration history. Migration 35 accepts the genuine v34 pending-source graph and rejects unexplained prior processing, unsafe indexes/options, inconsistent source records or populated new result collections before altering target definitions. Applied migrations 1–34 are unchanged; this historical migration description is not an instruction to downgrade or stop a newer database at version 35. Supplier processing additionally requires its owning schema/graph from the [supplier runbook](supplier-documents.md).

The payment processor claims only `payment.ocr.requested`; the separate supplier processor claims only `supplierdocument.ocr.requested`. Their bounded claim policies use a 30-second lease, 60-second processing deadline and five-attempt limit. Original access is additionally bounded by current private-read policy. Billing or Procurement supplies the immutable submission/version through its owning source; Documents proves its exact pin, original generation/hash, scanner/decoder records, lifecycle and current policies. A durable service read grant precedes byte access. File I/O and OCR run outside retried Mongo callbacks; current lease/policy/source/grant checks surround the atomic result, audit and queue receipt. A missing required audit rolls back publication.

The processor captures the admitted private-read deadline before opening/processing the source. Re-reading current source/policy after OCR must **not renew that consumed window**. Payment and supplier paths reject an expired captured deadline before preparing result writes, check the persisted timestamp again after awaited identifier allocation, and retain final transaction fences. Late output cannot create a partial extraction/audit/processing receipt or financial effect. A bounded safe timeout failure may be recorded under a still-current job lease; it neither reopens evidence nor extends private access. Retry requires a new genuine admitted attempt, not a patched old deadline.

Budget the whole admitted read/proof/OCR/result path against the shortest applicable private-read, claim, policy and engine deadline. The native supplier acceptance fixture explicitly used a **ten-second private-read lease within the existing cap**. This is synthetic fixture policy, not a production default, production approval or reason to widen limits automatically. Measure the actual host and independently approve its finite read and processing policies for the exact consumer/store/pipeline before enabling it. Local successful output alone supplies none of those approvals.

Results deduplicate by evidence version, purpose, model checksum and preprocessing version. Committed results recover from the original receipt under a current claim without reading or processing the file again. Transient failures record bounded safe codes and retry; terminal failures do not create suggestions. Late output from a lost lease or expired original-read grant cannot publish. Submitted evidence is immutable. The linked [payment replacement workflow](payment-declarations.md) preserves historical results and creates a new eligible source/pin; old results must never be reassigned to a new review.

The API rechecks the current buyer, branch membership, session, declared revision and exact submitted reference before returning a derivative. It repeats original eligibility checks and requires the complete result/audit/receipt graph plus a new derivative-read audit; it returns `private, no-store`. Raw recognized lines stay in private persistence, while the buyer receives bounded field candidates, locations, uncertainty and provenance. Read audits identify actor/resource/version/time/purpose/correlation without copying extracted bank values. The OCR service identity must have no Billing/Accounting write grants; Documents-owned fences and queue/ID operations remain required. Actual database privileges, denied network egress, immutable installations and host acceptance still require deployment verification.

The separate [payment verification](payment-verification.md), [allocation](payment-allocation.md) and [after-sales](after-sales-cases.md) owners define their connected local workflows and remaining gates; an OCR result does not grant their permissions. Required image/security/independence stay mandatory during an OCR outage. Never send originals or extracted bank data to a cloud OCR/general model, notifications or ordinary logs. Similarity investigation, representative calibration, retention/restore and actual service credential/egress checks remain open. Local synthetic processor/runtime/browser evidence does not establish hosted processing or operational acceptance.

## Finance submitted-payment viewing

`/billing/payment-reviews` requires an explicit current `payment.review.read` grant in the relevant fulfillment scope and `invoice.read` for every referenced invoice. Verified provider/session assurance and active application membership still apply. The Finance v1 template/packs are unchanged; the optional permission suggestion must be deliberately reviewed and granted through access administration. System administration, a Finance label, assignment, or payment verification permission alone grants no private viewer access.

The queue excludes drafts and applies both scopes before pagination. Detail checks the complete immutable declaration/submission/invoice source graph. The Billing-owned read adapter exposes only the submitted reservation, reference and original uploader; it cannot admit uploads, change a draft or pin another submission. Original reads reuse current security eligibility, bounded read leases, actual-file hash verification, required audit and final/renewal authorization. Derivative reads reuse the exact-source result graph and current eligibility without opening the original. Revocation, changed revisions, unavailable policy or required-audit failure prevent the affected read.

The screen presents declared values, issued invoice totals, the submitted original and separate OCR candidates. Invoice totals are explicitly not remaining AR. Preview bytes are checked again against the expected SHA-256, retained only in an in-memory blob and revoked when closed, replaced, offline or unmounted. All four reviewer routes require authenticated POST, exact Origin/CSRF and expected actor; original/OCR reads additionally require the declaration revision and exact evidence reference. Responses are private/no-store. Read audits record the reviewer and resource without copying bank values into logs.

This viewer neither asserts person-level decision independence nor approves funds: those remain mandatory prerequisites of the later financial decision. Approved receiving-account versions, bank corroboration, correction writes, assignments, replacement/rejection, canonical receipt, allocation and after-sales are not enabled by this read permission. Local synthetic access is not a live grant, provider acceptance or launch authorization.

## Human review corrections

The same Finance workspace can compare the buyer declaration, original image, immutable OCR candidates and current human observations. Saving observations requires a separately approved `payment.review.correct` grant in every invoice's fulfillment scope, both viewer permissions and a second factor completed within five minutes. Finance v1 packs do not gain this permission automatically. Unknown observations remain null; amounts, dates and times use the bounded canonical contract. Account/bank text read from the image is an observation, never an approved receiving-account identity. A save requires an actual change and a reason, with an explicit preview before sending.

Run forward migration 36 explicitly with writers quiesced. Applied migrations 1–35 are unchanged. The new empty `paymentReviewHeads` and `paymentReviewCorrections` collections use strict schemas, unique declaration/revision and identity indexes. Preflight rejects unexplained existing corrections/effects, exhausted or malformed allocators, unsafe retention/uniqueness/options and preserves stronger existing validators. It creates no grants, person evidence, policy approvals or financial records.

The correction owner checks the current submitted declaration, exact pinned evidence version/hash and completed extraction in the same transaction as the immutable correction, current head, required audit, receipt and durable metadata-only outbox event. Original eligibility and authority are fenced again before return. History links each before/after version with its predecessor and original OCR baseline; missing history/audit/receipt/outbox or stale revision fails closed. Every correcting account and its then-current verified-person evidence (or explicit unknown state) are retained. This is provenance, not a claim of financial independence. The separate bank decision must re-resolve the original recorder/uploader and every corrector against current trusted person/equivalence evidence and consume the exact current review revision.

The submitted buyer declaration and its initial submission `reviewRevision` remain frozen. The separate review head starts at revision zero when absent and advances on each correction. Bank approval must bind this current head, not infer that the submission's frozen revision is the current decision version. Replacement and later decision workflows must coordinate new bindings and invalidate prior decisions; neither is implemented by correction writes. Corrections require completed OCR and current private-image eligibility. They cannot be used as an unaudited exception during an OCR outage.

All correction query/write/recovery routes require authenticated POST, Origin/CSRF and expected actor; writes also require an exact review `If-Match` and idempotency key. Queries require exact declaration/submission/image/extraction binding and are private/no-store. The latest twenty human versions are displayed while the owner validates the complete history. No observed values or reason are copied to the browser's persistent operation journal: it stores only actor, operation, key and time. A lost response recovers the original metadata receipt under current scoped fresh authority, including after reload; missing or mismatched receipts never authorize automatic resubmission or closing an unknown attempt. Private field reads still require current original/derivative eligibility.

Pending release gates include history-load performance, accepted provider MFA, trusted-person operations, actual scanner/storage/database/worker deployment, backup/restore, real approved receiving accounts/bank procedures and the branch pilot. Connected local verification/allocation is recorded in its own runbooks and the ledger, not established by this correction permission. Neither a correction nor its outbox event confirms a bank deposit, alters AR/cash, sends a real external message or executes a transfer.
