# Private bank statement staging

The Finance workspace is `/billing/bank-statements`. It previews an approved bank CSV export against an explicit approved receiving-account version, then stores the original bytes and parsed rows privately for reconciliation. A staged row is not a confirmed bank receipt, verified payment, accounting entry or invoice allocation.

## Operational inputs

Migration 38 creates empty profile and import collections. It creates no bank profile, account, grant, balance or production fixture. Before real use, Finance must approve the actual bank export samples, exact header order, delimiter, date and decimal formats, credit/debit markers, canonical bank code, fulfillment scope, independently established source, named owner, approval reference and validity interval. Profile records are controlled deployment inputs; there is no public profile-creation endpoint. The bank-channel/person-authority decisions already pending in the decision ledger still apply.

The versioned `bank-csv-v1` parser accepts strict UTF-8 CSV, with an optional UTF-8 BOM, quoted fields and escaped quotes. Its eight ordered columns represent transaction ID, booking date, direction, amount, payer, reference, receiving account number and currency. Column labels are configured by the approved profile. Dates are explicitly `yyyy-MM-dd` or `dd/MM/yyyy`; amounts have a configured decimal separator and no grouping separator. Unsupported formats are rejected, not guessed. A real bank format outside these contracts requires an additional reviewed parser and actual source samples before activation; converting arbitrary data into these columns does not establish bank provenance.

`identityNamespace` is an approved bank source identity domain, not a user-selected label or profile version. Configure it only when the bank documents stable transaction IDs within a physical account. Retain that domain across profile revisions and overlapping exports. A null namespace or absent transaction ID leaves the row explicitly unidentified. A typed reference, file hash, filename, payer name or account-lineage/version ID must never substitute for bank transaction identity.

## Workflow and privacy

1. Use separately assigned `bank.statement.read` and, for staging, `bank.statement.stage`. Full receiving-account read permissions are also required. Staging requires fresh MFA. These are Finance grant suggestions, not automatic additions to Finance packs or new role templates.
2. Select a current approved format and receiving-account version. Upload the original file (at most 256 KiB and 500 rows). The browser keeps file contents in memory only.
3. Inspect exact incoming/outgoing totals, rows and findings. Wrong account/currency, malformed values, unsupported encoding/columns, future dates or excessive totals block the entire import. Repeated or missing identity, repeated references and unidentified payer remain visible reconciliation findings. File-local duplicate findings are advisory; cross-import canonical reconciliation is still pending.
4. Record the independently obtained source reference, an explanation and explicit source attestation. Review the frozen confirmation before saving. The server repeats current profile/account/version checks and requires the exact preview binding to the original bytes.
5. An immutable import, source bytes, parser/profile/account snapshots, original recorder/person provenance, audit, original operation receipt and metadata-only outbox effect commit together. The profile, account and actor/session/grants are fenced. A missing or damaged provenance component fails closed. Unknown maker-person evidence is retained explicitly; it cannot later satisfy independent financial approval.
6. Reopen the import or explicitly download its original. Originals are bounded private binary values in MongoDB, never static assets, public URLs, event payloads, logs or browser storage. Downloads require current scope, are audited, are served as an attachment with no caching, and are checked against the original digest in the browser. Apply the approved production database access, encryption, retention and backup controls to these financial records.

Only actor, operation, request key and time enter the browser recovery journal. After a lost response, **Periksa hasil** looks up the original result; it never resends the source or fabricates a failed/closed outcome. Historical reads and recovery retain the old approved account/profile snapshots after later changes. New staging requires a new preview using the current account and current valid profile.

## Reconciliation and release boundaries

Renamed/repeated/overlapping imports remain separate source evidence with consistent identity candidates. No uniqueness constraint claims that staging confirms a transfer. The subsequent reconciliation owner must deduplicate a confirmed canonical identity by physical account and bank identity domain/transaction ID, retain distinct transfers with reused references, adjudicate missing/ambiguous identities, bind independent bank checks and payment evidence, and post one actual receipt/journal before allocations become available. Unknown payers remain unidentified/suspense; importing them does not authorize customer allocation.

Actual approved bank samples/channels, operator acceptance, source provenance, canonical confirmation/matching, cash/allocation and supplier/refund integration remain required work. Local fixtures are synthetic even when they run through real Next, .NET and MongoDB. Staging/provider acceptance, migration/restore, Vercel/API/worker/private storage connections, one-writer cutover and the approved branch pilot remain M6 gates.
