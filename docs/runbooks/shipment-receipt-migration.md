# Authenticated shipment receipt upgrade

Migration 26 installs `shipmentReceiptChallenges` and `shipmentReceipts`. Migrations 1–25 stay unchanged. Dispatch, Surat Jalan issuance, scanning a QR and recipient acceptance remain separate facts; this upgrade invents no historical acceptance.

1. Select the reviewed release and approved environment. Pause/drain all business writers and take a coordinated backup of orders, reservations, stock movements, dispatches, issued documents, receipt collections, identity/person authority, audit, original command receipts, counters and outbox. Keep private uploaded evidence under its separate storage backup procedure.
2. Run the existing worker migration entry point with the approved environment configuration. Verify version 26 and byte-equivalent predecessor migration receipts. Preflight inspects **both** new collections and reverse receipt effects before any owner DDL. Unexpected data, TTL/partial/sparse/hidden indexes, extra uniqueness, unsafe counters and incompatible collection options stop the upgrade. Preserve unexpected data for review; do not delete it to pass preflight. Compatible stronger empty validators and existing safe counters survive.
3. In isolated staging, use a dispatched shipment with an issued Surat Jalan. The assigned courier needs `delivery.evidence`; the shipment workspace also needs `shipment.read`. The intended recipient needs current approved buying membership and `receipt.accept` for the actual order. Branch/division authority still requires the PIC permission; organization-wide scope requires its explicit pack. Existing role templates are not widened.
4. Both courier and recipient require reviewed person authority proving they are different people. Candidate listing uses approved application membership and profile facts, never a pretend session or courier-entered phone/email. The recipient must authenticate in their own session; a shared tablet must use a separate recipient session. Real person-source approval and actual Auth0 acceptance remain release gates.
5. Issue a recipient-bound QR, review the exact document version and dispatched package definitions, then record accepted, rejected and missing quantities. Whole packages plus an explicit loose remainder must conserve every dispatched base unit. A discrepancy requires a reason. Consent is an unchecked explicit step, bound to the server's versioned Indonesian statement, recipient, document hash, quantities and server time.
6. Rehearse five failed-token attempts, the 15-minute expiry, courier/wrong-recipient denial, independent-person revocation, membership/session expiry and concurrent confirmations. One receipt, challenge consumption, audit, original command receipt and ID-only outbox commit atomically. No receipt action changes stock, produces an invoice, posts cash, or executes a refund. Discrepancies are recorded for the later after-sales workflow.
7. Lose a committed response, reload and recover by the original account/operation/key. Recovery only looks up the accepted record; it cannot resend or close an uncertain request. A QR secret is generated randomly, stored only as SHA-256, and disclosed only in its original successful response. Recovery cannot reconstruct it. A deliberate new challenge can be issued after reconciliation when no receipt exists, subject to the per-shipment hourly limit. A consumed or damaged receipt cannot be replaced with a new request key.
8. Restore the coordinated set into isolation. Accepted receipt/source/document/audit/operation relations must verify before any read or retry. A missing root with surviving consumption or acceptance effects is damaged history, not an unreceived delivery. Retain expired challenges; TTL deletion would destroy accepted provenance.

The browser keeps the QR secret in memory and a URL fragment, removes the fragment before asynchronous account work, and sends it only in authenticated POST bodies. It is absent from operation journals, query strings and outbox payloads. Signing in requires rescanning rather than persisting the secret through the authentication redirect. Local disconnected entries remain unsent and are not durable; the page states this explicitly.

This is authenticated QR consent with exact quantities, not a certified electronic signature or the completed tablet drawing/photo evidence workflow. Private signature/image attachments, delivery attempts/returns, after-sales routing, invoice eligibility, broader document corrections, live provider/deployment acceptance, restore rehearsal and pilot remain required. This runbook authorizes no external message, purchase or real-data cutover.
