## Delivered boundary

An interrupted request has three explicit outcomes: committed, closed_no_effect or not_confirmed. An absent receipt alone cannot prove failure. Explicit closure writes a permanent versioned marker under the original unique actor/operation/key in the same Mongo transaction protocol as the original command. Whichever transaction commits first determines the outcome. All six raw/reviewed propose, approve, reject and withdraw entry points reject a valid closed key before replay/body-history processing. A delayed command cannot reopen it or repeat effects.

Existing committed receipts still validate immutable proposal/history/result relationships and the current exact target-specific receipt appointment. Their original business result and timestamp are preserved, including after the deliberately withdrawn target loses positive authority or a preview expires. Recovery does not reverse an existing change. Closed-key lookup needs current receipt-read authority; creation of a new closure additionally needs the original command permission, fresh MFA, current person proof and an explicitly appointed receiptResolve capability bound to the exact operation/key. Neither capability grants target discovery, names or proposal detail. Default production trust remains unavailable; no appointment is seeded.

One strict parser checks the exact common and closure BSON shape, schema/type/version, actor/key, dates, fixed discriminator, authority epochs, policy pin and bounded reason/correlation. Partial, mixed, access-operation or malformed markers fail closed. The receipt row holds no fabricated proposal/history/result IDs. The existing shared receipt collection permits this additive marker and already supplies the unique actor/operation/key index; no migration or TTL rule changed. Future retention/archival must preserve the permanent key barrier. Arbitrary database deletion is not a supported operation.

The protected operations/resolve route accepts only the original operation, Idempotency-Key and reason; it does not reconstruct lost private request bodies. Both query and resolve return a validated state/result/recordedAt envelope. This intentionally replaces the previous local, unreleased boolean person-receipt response. Verified sessions, exact origin, anti-forgery and expected-actor checks remain in force. Current authorization is rechecked after final receipt/audit/session awaits, and failure rolls back the closure, read audit and fences.

The Indonesian recovery screen offers explicit confirmation and reason for closing an unresolved reference. It retains only actor/operation/key metadata across reload. A valid committed or closed response clears that reference and any matching in-memory uncertain command; a new action requires fresh selection/review. Missing, malformed, denied, timed-out and uncertain responses keep recovery locked. An operation_closed command error alone cannot clear the journal. Actor/view changes discard late results before journal cleanup. Receipt-only recovery remains available when independent account discovery is unavailable; private lists/details are hidden. The shared journal keeps existing access/identity/organization routing behavior.
