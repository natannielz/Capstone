## 28 September 2026 — CAT01.1 explicit identity and package rules

Status: locally accepted pure-domain prerequisite after bab3707. This does not complete CAT01 or any production acceptance row. The [catalog plan](../superpowers/plans/2026-09-28-report-catalog-packaging.md) and [97-item register](../requirements/unit-toko-report-2026-09-28.md) retain their full scope.

Five domain files under backend/src/UnitToko.Modules/Catalog now define Sku, immutable VariantDefinitionVersion, DefinitionInput/SkuDefinitionChange, CatalogPolicy and Gtin. They accept explicit IDs, revisions, UUIDs and time; they allocate no identity, read no clock, authorize no writer and change no stock.

- Two packages both labelled Dus retain independently supplied contents. Family/name equality, source codes and images never infer physical equivalence or conversion.
- Label, image and order-rule correction creates a new immutable definition on the same SKU; kind, base unit, counted contents and current intrinsic attributes are material. Material changes require an explicit new SKU, UUID, code and definition with predecessor. Equivalent-content replacement is permitted when explicitly requested; the old SKU is never implicitly retired or reactivated.
- SKU aggregate and definition revisions are independent. Current pointers, owner/family IDs and predecessor identity are validated structurally; future storage must establish ownership and reserve identifiers. Checked revision exhaustion produces a controlled error. Explicit timestamps may share an instant and normalize to UTC without backdating.
- Contents are positive Int32; command package count, minimum order packages and increment use the existing 1..1,000,000 bound independently. Multiplication widens to Int64 before calculation. Ordering admissibility and replenishment thresholds remain separate contracts.
- SKU normalization rejects non-ASCII code characters before uppercase conversion. GTIN accepts supplied ASCII strings of 8/12/13/14 digits with a valid check digit, preserves raw leading zeros and exposes a 14-digit comparison key. Strict JSON rejects numeric/null GTIN inputs. Validation is neither identifier allocation nor ownership/authenticity proof.
- Immutable ordinal attributes reject normalized-key collisions. Bounded Unicode text preserves valid supplementary characters and rejects unpaired surrogates. Image references carry no document eligibility or delivery capability.

Technical input limits are label160, base-unit code64, physical-item key128, attribute key64/value256/count32 and image count16. These are validation limits, not approved pricing, audience, unit-registry or commercial policies. PackageKind is loose/sealed/other. Mixed bundles and measured goods are outside this counted-content contract.
