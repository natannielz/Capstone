# Shipment preparation and dispatch

`/fulfillment/cases` connects finalized invoice items to immutable complaint intake under separate `case.request` and `case.read` grants. Buyers review original packaging and accepted base quantities before confirming reported items. Lost-response recovery uses the original actor/key without resending; case readers see only scoped sale/item/problem facts. Intake does not authorize returns or financial settlement. See [case storage and workflow](../../../../docs/runbooks/after-sales-cases.md) and the [progress ledger](../../../../docs/quality/production-progress.md) for remaining approval, inspection, credit/refund and release gates.

`/fulfillment/preparations` connects the scoped `shipment.prepare` permission to accepted store demand from the Ordering owner. Store acceptance is a separate permission and prerequisite. Staff choose explicit complete packages, review their contents and partial quantities, then save a shared versioned preparation. A purchase minimum does not prevent partial fulfillment. The screen receives no price, margin or other store's lines.

Ordering verifies the original order, current decisions and reservation history in the caller's Mongo transaction. Fulfillment owns the preparation head and immutable versions; saving also commits its audit, original receipt and private-reference outbox event. Competing revisions, cancellation, revoked access and expired sessions cannot commit stale work. Saving a preparation neither dispatches stock nor changes money. A later dispatch must revalidate and consume the actual remaining reservation through the owners' transaction interfaces.

The dedicated `fulfillment.preparation` recovery adapter only looks up the original actor/operation/key. Browser storage contains that reference and time, never the order, address or quantities. Lost responses are not retried automatically. Recovery can return an older saved version after another staff edit; the screen then fetches the current plan. A cancelled order retains its immutable preparation but cannot accept another save.

`/fulfillment/dispatches` connects current prepared demand to explicit physical-lot selection and courier assignment. This combined workflow requires both `shipment.dispatch` and `shipment.assign`; existing templates are not silently widened. The courier must currently have scoped read/attempt grants and approved assignment membership. No first lot or courier is selected automatically. The server preview binds the current preparation, reservation/stock revisions, courier and approved source/cost facts. Changing any of them requires another review.

Dispatch writes one immutable shipment, consumes exact reserved packages through Ordering, and changes physical stock through Inventory in the same Mongo transaction as audit, receipt, document number and private-reference outbox. Cancellation releases only the remaining reservations; accepted shipment and original order snapshots remain intact. A stale preparation cannot be dispatched twice. The `fulfillment.shipment` browser recovery adapter stores only the original actor/operation/key/time and performs lookup without resubmitting a dispatch. Recovery can return the original accepted result after later preparation edits, cancellation or courier revocation, subject to the caller's current scoped dispatch access.

`/fulfillment/shipments` uses the separate `shipment.read` permission. Assigned couriers see only their assigned shipments; ordinary buyers see their own permitted orders' shipments. Branch-wide access requires the explicit PIC grant. Scoped store readers can inspect their permitted store/channel. Scope filters precede pagination, and the original dispatch, order/reservation and physical movement history is verified before disclosure. Final grant/membership/session checks protect both detail and the paging result. The screen shows only actual dispatched package quantities and destinations, without internal cost/approval/stock records, and preserves accepted dispatch facts after remainder cancellation. It does not claim receipt acceptance. Account navigation, exact sign-in return path, keyboard focus return and offline/stale messaging accompany the read-only view. Read access does not grant dispatch, receipt acceptance or administrative access.

Migration 23 installs preparation storage; migration 24 installs canonical dispatch storage. See the [preparation upgrade](../../../../docs/runbooks/shipment-preparation-migration.md), [dispatch upgrade](../../../../docs/runbooks/shipment-dispatch-migration.md) and single [progress ledger](../../../../docs/quality/production-progress.md). Connected local tests use synthetic identities and approved business/source/cost inputs. The production service has no permissive admission reader. Separate assignment/handoff and reassignment, scan assistance, delivery attempts/returns, recipient proof, issued Surat Jalan documents, invoices and actual provider/production acceptance remain open. A dispatch number is not proof of delivery or an invoice.
