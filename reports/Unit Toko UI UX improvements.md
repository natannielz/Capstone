# Collapse twenty-four stylesheets into one operational system

Unit Toko looks and behaves inconsistently mainly because of its CSS cascade, not because it lacks components. Twenty-four global, version-numbered stylesheets are imported on every route. Together they hold about 5,900 lines, 64 `!important` declarations and no `@layer` rules. Because CSS outside a layer beats every layered rule, they override the Tailwind v4 and shadcn styles the team already ships. That includes Field, Form, Empty, Combobox, Table, Skeleton and Sidebar primitives, and the self-hosted DM Sans font. The way to a consistent, production-ready UI has two halves. The first is a single token-driven design system, reached safely: put the legacy CSS in a low-priority cascade layer behind Playwright screenshot baselines, then replace one screen family at a time. The second is a single operational grammar for every role workspace. That means one work-queue table, one review panel that also acts as the maker-checker confirmation, one status dictionary, one outcome component that handles a lost response by re-sending the same idempotency key, and one form stack. The Indonesian layer is mostly a consolidation job. The app already uses "Anda" and WIB consistently, but money and dates are formatted by hand-written `Intl`/`toLocaleString` calls spread over dozens of files, and the default number of IDR decimals differs between ICU versions. Measured colour contrast fails WCAG 2.2 AA in the status badges (3.3–3.8:1), the muted text (2.9–3.3:1) and the orange focus ring (2.6–2.9:1). Field workflows should assume the typical user is on Android (80–85% of Indonesian mobile traffic), a 360-pixel screen and a flaky network. Engineers should start with two low-risk changes, a screenshot baseline plus layer quarantine and then tokens, contrast, font and formatters, before building patterns and field flows. The roadmap at the end lists the phases and acceptance checks a machine can verify.

## Twenty-four unlayered stylesheets outrank every component the team writes

### Why the cascade, not the components, causes the inconsistency

The root layout imports `globals.css`, `polish.css` and 22 files named `orders-v5`, `storefront-v7`, `workspace-v14`, `operations-lists-v15` and so on, in version order. None of them declares a cascade layer (local codebase observation, `frontend/src/app/layout.tsx`, 19 Oct 2026). Tailwind v4 puts its own CSS into the native layers `theme, base, components, utilities` ([Tailwind](https://tailwindcss.com/docs/theme)). Under the cascade rules, **styles not defined in a layer always override styles in any named or anonymous layer, whatever their specificity** ([MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/@layer)). So every legacy selector beats every utility class and shadcn component style, and engineers have answered with more specific selectors, more `!important` and another `-vNN.css` file. Next.js makes this worse in two ways. It **does not remove global stylesheets when the user navigates between routes**, and production CSS order follows import order ([Next.js](https://nextjs.org/docs/app/getting-started/css)). That means the 2,566-line storefront file, the landing and carousel CSS, and the motion rules all ship to, and can leak into, the billing review desk.

Fonts show the same problem. The layout already self-hosts DM Sans (variable) as `--font-body` and Archivo Black as `--font-display` through `next/font/local`. But `globals.css` hard-codes `font-family: "Segoe UI", Arial` on `body`, `"Trebuchet MS"` on `h1`/`h2`, and Trebuchet again on metric cards (local codebase observation). Those are Windows system fonts. On Android, which carries **79–85% of Indonesian mobile traffic** ([StatCounter](https://gs.statcounter.com/os-market-share/mobile/Indonesia)), they fall back to whatever the device has, so older screens and newer screens render in different typefaces. The status badges show a third symptom. They are styled by their Indonesian label text (`.status-badge[data-status="Menunggu tinjauan"]`, with `!important` padding and radius). If someone rewords a label, the badge silently loses its colour.

The components exist; the cascade is what defeats them. `components/ui` already contains about fifty shadcn primitives, among them `field`, `form`, `empty`, `kbd`, `combobox`, `table`, `pagination`, `skeleton`, `sidebar` and `sonner` (local codebase observation). The job is mostly to let them win, not to write them again.

### A three-tier token file replaces hex values scattered across overrides

In Tailwind v4 the design system lives in CSS. Raw values are custom properties on `:root`. An `@theme inline` block maps them into utility namespaces (`--color-*`, `--radius-*`, `--font-*`, `--spacing`). Use `inline` whenever a token points at another variable; without it, the `var()` resolves where the theme variable is defined and can pick up the wrong value ([Tailwind](https://tailwindcss.com/docs/theme)). shadcn's current convention pairs each surface token with a `-foreground` token. Teams add their own semantic pairs, such as `--warning`/`--warning-foreground`, the same way. Every radius derives from one `--radius` ([shadcn](https://ui.shadcn.com/docs/theming)).

For Unit Toko that gives one `tokens.css` with three tiers. The first tier is primitive ramps (teal, neutral, amber, red, green), optionally with `--color-*: initial` so nobody reaches for `bg-red-500`. The second is semantic pairs: the shadcn set, plus `success`, `warning`, `info`, and one tone per status class (`--status-progress`, `--status-attention`, `--status-done`, `--status-danger`, `--status-neutral`, each with a foreground). The third is the `@theme inline` mapping, including `--font-sans: var(--font-body)`. Converting today's hex values (`--primary: #087f8c`) to OKLCH is optional, because Tailwind's opacity modifiers work through `color-mix()` either way.

**Defer dark mode.** The repo has no `ThemeProvider`, and `next-themes` defaults to `attribute="data-theme"`. Class-based `dark:` utilities therefore stay inactive until the provider is set to `attribute="class"` ([next-themes](https://github.com/pacocoursey/next-themes)). Wiring dark mode now would double the screenshot and contrast test matrix before the light theme even passes AA. Add the `.dark` token block later, when the light tokens are proven.

### Quarantine first, then strangle by screen family

The safe consolidation sequence starts by changing who wins the cascade, not by deleting code. Remove the 23 JavaScript CSS imports from `layout.tsx` and import those files from `globals.css` into a dedicated layer. The first `@layer` statement fixes the layer order:

```css
@layer theme, base, legacy, components, utilities;
@import "tailwindcss";
@import "tw-animate-css";
@import "../../vendor/shadcn-tailwind-4.13.0.css";
@import "./legacy/polish.css" layer(legacy);
@import "./legacy/storefront-v7.css" layer(legacy);
/* …remaining files in today's order… */
@import "./tokens.css";
```

Legacy rules still beat Preflight (`base`), so today's look survives. But new utilities and shadcn components (`components`, `utilities`) now win **without `!important`**. JavaScript imports cannot assign a layer, which is why the files have to move into CSS `@import … layer()`. There is one trap. For `!important`, the layer order reverses: **important declarations in earlier layers beat important declarations in later layers** ([MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/@layer)). The 64 legacy `!important` rules therefore become harder to override once layered. Remove them first, or isolate the files that use them in a `legacy-important` layer and fix those early. Whether `@tailwindcss/postcss` 4.2.1 keeps a user-declared layer between `base` and `components` has not been verified. A 30-minute spike that inspects the built CSS should settle it before the PR.

Two Playwright features make the migration measurable. `toHaveScreenshot()` stores golden images per browser and platform and compares later runs against them. The docs warn that baselines must be produced in the same environment that runs the tests, and they support `maxDiffPixels`, `threshold` and a `stylePath` stylesheet that hides volatile regions ([Playwright](https://playwright.dev/docs/test-snapshots)). `page.coverage.startCSSCoverage()` returns the byte ranges each stylesheet actually used during a journey (Chromium only) ([Playwright](https://playwright.dev/docs/api/class-coverage)). Run the same 30–60 role-by-screen journeys for both: screenshots to lock the look, coverage to map which legacy selectors are live. Pin the CI environment to one Playwright Docker image, because the current Windows-only fonts make cross-OS baselines especially noisy. Treat "unused" as "unused in tested flows", since coverage only sees the states the journeys reach.

Then migrate one **screen family** at a time. Tokens and fonts come first, followed by the app shell, the primitives, the operations lists, order and fulfilment detail, and account and login. The public storefront, catalog and landing pages go last, because they carry the largest legacy files and GSAP. Each step does four things: rebuild the screens on the primitives, re-baseline the intended diffs, delete the selectors coverage shows are dead, and keep every other screenshot green. CI guards stop the pile regrowing: stylelint's `declaration-no-important` outside the legacy folder, a check that fails on any new `*-v[0-9]*.css` file, and a lint rule against legacy class names in new TSX. After migration, about 95% of styling should live in Tailwind utilities inside components (`cva` variants). CSS Modules should be kept for genuinely bespoke visuals such as marketing hero art and print layouts, which load only on the routes that import them. Global CSS should shrink to tokens, `@layer base` element defaults and third-party skins in `@layer components`.

### One primitive library per component, plus a small set of owned patterns

The frontend depends on both `radix-ui` 1.6 and `@base-ui/react` 1.7. Since July 2026 shadcn **defaults to Base UI but explicitly keeps Radix supported and not deprecated**, and says existing projects do not need to migrate ([shadcn](https://ui.shadcn.com/docs/changelog/2026-07-base-ui-default)). Base UI is releasing quickly; v1.9.0 on 9 Oct 2026 brought accessibility and focus fixes ([Base UI](https://base-ui.com/react/overview/releases)). The risk of running two libraries is two portal, focus-trap and dismiss-layer stacks interacting, for example a Base UI Select inside a Radix Dialog. Pick **one library per component type**. Base UI is the better default for new and migrated primitives. Keep Radix only where no Base UI equivalent exists yet, and record the choice in `components.json` and an ADR.

The two libraries handle the same layer of accessibility. Radix supplies ARIA roles and attributes, focus management and keyboard patterns, and says outright that labels are the developer's job ([Radix](https://www.radix-ui.com/primitives/docs/overview/accessibility)). Base UI does the same, adds automatic label association in its Field and Form components, and puts colour contrast on the developer ([Base UI](https://base-ui.com/react/overview/accessibility)). Unit Toko therefore still owns accessible names for icon buttons, visible labels, token contrast, non-colour status cues, 24-pixel targets, error summaries, `aria-live` announcements when a table refreshes asynchronously, and a skip link with proper landmarks.

On top of the primitives, the app needs a small set of **owned pattern components**, built only from primitives and tokens and never from raw hex:

| Component | What it does |
|---|---|
| `PageHeader` | Standard page heading |
| `FilterBar` | Standard filter row |
| `DataTable` | TanStack Table headless logic over shadcn markup; TanStack Table is headless by design ([TanStack](https://tanstack.com/table/v8/docs/introduction)) and is not yet installed |
| `StatusPill` | Status badge driven by the status dictionary |
| `Stepper` and `ActivityTimeline` | Lifecycle and history display |
| `ReviewPanel` | Review-before-decide summary and confirmation |
| `OutcomeState` | Shows the result of a mutation, including unknown outcomes |
| `EmptyState` | Empty lists and screens |
| `Skeleton` | Loading placeholders sized to match the final layout |
| `Field` with `ErrorSummary`, `CurrencyInput`, `QuantityStepper` and `EntityCombobox` | Form building blocks |
| Toast wrapper | One `toast()` call, so Sonner can later be swapped for the July 2026 shadcn Toast without touching call sites ([shadcn](https://ui.shadcn.com/docs/changelog/2026-07-toast)) |

Today `button:disabled` uses `cursor: wait` (local codebase observation), which mixes up "not allowed" and "busy". The Button contract should separate the two: `disabled` for not allowed, and `aria-busy` with a spinner for a request in flight.

Typography for operations screens should use a 14px base:

| Token | Size / line height | Use |
|---|---|---|
| `--text-xs` | 12/16 | Meta |
| `--text-sm` | 13/18 | Dense table cells |
| `--text-base` | 14/20 | Body and form controls |
| `--text-lg` | 16/24 | Section titles |
| `--text-xl` | 20/28 | Page titles |
| `--text-2xl` | 24/32 | KPIs |

Use weights 400, 500 and 600 only. Put `tabular-nums` on every money, quantity and KPI cell ([Tailwind](https://tailwindcss.com/docs/font-variant-numeric)). Keep DM Sans, since it is already self-hosted, if it renders tabular figures. If it does not, Inter documents a `tnum` feature intended for comparing columns of figures ([Inter](https://rsms.me/inter/)). Set density with a `data-density` attribute on the workspace shell, driving component tokens (`--row-h` 40/32px, `--control-h` 36/32px, `--cell-px`). Do not redefine the global `--spacing`, which would also shrink page gutters.

### Performance comes from server rendering and keeping marketing weight off ops routes

The targets are **LCP ≤ 2.5 s, INP ≤ 200 ms and CLS ≤ 0.1 at the 75th percentile**, measured separately for mobile and desktop ([web.dev](https://web.dev/articles/vitals)). On data-dense screens INP is usually the hardest. It grows with DOM size and with the work done in event handlers ([web.dev](https://web.dev/articles/optimize-inp)), so cap table DOM with server-side pagination of 25–100 rows, or with TanStack Virtual above about 200 rows ([TanStack Virtual](https://tanstack.com/virtual/latest/docs/introduction)). Put filter state in `useTransition`. Backend reads that take several seconds call for a streaming layout. Render the shell, PageHeader and FilterBar as Server Components straight away, give each slow region its own `<Suspense>` with a skeleton the same size as the final content, and start fetches in parallel. `loading.tsx` already gives an instant streamed fallback on navigation ([Next.js](https://nextjs.org/docs/app/api-reference/file-conventions/loading)). Keep `'use client'` on leaf widgets, because everything a client file imports joins the client bundle ([Next.js](https://nextjs.org/docs/app/getting-started/server-and-client-components)).

For mutations, `useActionState` provides pending and server-error state, and `useOptimistic` rolls back automatically on failure ([React](https://react.dev/reference/react/useOptimistic)). Use optimism **only for reversible status changes, never for payment allocation, stock adjustment or sealed checkpoints**, where the UI must show the confirmed server result.

The project builds with `next build --webpack` on Next 16.3.4, while Turbopack is the Next 16 default ([Next.js 16](https://nextjs.org/blog/next-16)). So measure with `@next/bundle-analyzer` rather than `next analyze`, which needs Turbopack ([Next.js](https://nextjs.org/docs/app/guides/package-bundling)). Move GSAP and the carousel behind `next/dynamic` in a `(marketing)` route group, and move landing and storefront CSS into that group's layout or into CSS Modules, so workspaces stop downloading them. Report real-user vitals by route and role. Office PCs and low-end Android tablets, not developer laptops, will decide the 75th percentile.

## One operational grammar should govern every role workspace

### Tables and queues: compact rows, saved views, urgency-first sorting

Mature design systems agree on how a data table is laid out. A toolbar holds search, filters, display settings and the primary action. Rows have checkboxes, and the header has a three-state "select all". Selecting rows brings up a batch-action bar, and row actions are disabled while it is active. Row actions sit inline when there are fewer than three and move to an overflow menu otherwise. Sorting has three states, and row heights come in 24, 32, 40 (the default), 48 and 64px ([Carbon](https://carbondesignsystem.com/components/data-table/usage/)).

NN/g adds that headers and the identifying column should stay frozen on large tables, that hiding columns must be easy and must show that columns are hidden, and that a table has four jobs: find, compare, view or edit, and act ([NN/g](https://www.nngroup.com/articles/data-tables/)). Numbers are right-aligned ([GOV.UK](https://design-system.service.gov.uk/components/table/)). SAP sets compact density at 32px for mouse and keyboard and cozy at 44px for touch, applied app-wide, and **never mixes the two on one page** ([SAP Fiori, via search summary](https://www.sap.com/design-system/fiori-design-web/v1-136/foundations/visual/cozy-compact)).

Filtering should apply instantly for a single choice. Use batch filtering with an "Apply" button when the user selects several facets or results return slowly, and offer per-category and global "clear" ([Carbon](https://carbondesignsystem.com/patterns/filtering/)). Work lists should use pagination or "Load more" that keeps the scroll position, not infinite scroll. Infinite scroll loses the user's place when they open a record and come back, which is exactly the list-detail-list loop of a review desk ([NN/g](https://www.nngroup.com/articles/infinite-scrolling-tips/)).

For Unit Toko this becomes one `DataTable` contract with compact 32px rows for desktop staff (Kepala Toko, billing, accounting) and cozy 44–48px rows on touch routes (Staf Toko). Each queue gets **named, URL-addressable saved views**. Jira Service Management models a queue the same way: a saved filter with chosen columns, usually sorted by SLA, with a clock showing time to the next target ([Atlassian](https://support.atlassian.com/jira-service-management-cloud/docs/what-are-queues/)). Ship role defaults, for example "Bukti bayar perlu ditinjau" and "Dana titipan belum dialokasikan" for billing. Sort by oldest waiting by default, and show aging as relative time ("Menunggu 2 hari") with the absolute time on hover. Escalate to a high-attention tone only past a defined threshold. On phones, picking and dispatch lists become cards showing identifier, status and quantity. Report tables keep horizontal scrolling with a locked first column and a visibly cut-off edge ([NN/g](https://www.nngroup.com/articles/mobile-tables/)).

Above the module queues sits one **"Pekerjaan saya"** home. It groups the items the current user can act on, decided by the server authorization the app already has, by action type: "Setujui pesanan", "Tinjau bukti bayar", "Konfirmasi substitusi", "Terima barang". Badge counts include only action-required items. Linear keeps "needs attention" apart from other updates for the same reason ([Linear](https://linear.app/docs/inbox)). Triage actions follow Linear's set: accept, decline with a reason, or snooze ([Linear](https://linear.app/docs/triage)). Shared desks need an explicit claim ("Ambil", "Ditangani oleh Rina") so two reviewers do not open the same proof.

### The review panel is the confirmation in maker-checker decisions

Use one `ReviewPanel` for every decision: approving spending, accepting orders, consenting to substitutions, verifying payments, allocating suspense funds, approving refunds and delegating access. It contains a summary list of exactly what will be committed, a "Sebelum → Sesudah" diff with changed values highlighted, and a plain-language consequence line. For reject or return-for-revision it adds reason chips and a note field. It ends with one primary button named with the verb and object ("Setujui pesanan PO-2026-0142 · Rp4.250.000").

Carbon's rules support this. Title and button should both name the action. A destructive action uses a danger variant. **One modal should never trigger another**, and a task that needs confirmation should not itself be in a modal ([Carbon](https://carbondesignsystem.com/patterns/dialog-pattern/)). NN/g warns that routine confirmations train people to stop reading them, and that dialogs should state the consequence instead of asking "Are you sure?" ([NN/g](https://www.nngroup.com/articles/confirmation-dialog/)). So the review panel is the confirmation. A second danger dialog is reserved for irreversible money movements: refunds issued, payment allocations and write-offs.

Three maker-checker behaviours need to be visible in the interface, not only enforced on the server. First, **self-approval prevention is explained in place**. On the user's own submission, the Approve button is replaced by a sentence naming who must approve, and a bulk approval lists the user's own items as "dilewati — pengaju sendiri". Second, **stale approvals are invalidated**. GitHub can dismiss approvals when new commits arrive and can require approval of the latest push ([GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)). Unit Toko's equivalent is the banner "Pesanan berubah sejak Anda membuka ulasan", shown with the diff, and Approve stays disabled until the reviewer looks again. Third, **step-up authentication keeps the user's place**. WorkOS advises carrying the original location and in-progress action through re-authentication and avoiding very short `max_age` values ([WorkOS](https://workos.com/docs/authkit/reauthentication)). So MFA should open over the review panel and keep the reason text, selection and idempotency key, then resubmit the original request. After a decision, a confirmation surface shows the reference number, what happens next and who acts next, and links to the timeline, following GOV.UK's confirmation page pattern ([GOV.UK](https://design-system.service.gov.uk/patterns/confirmation-pages/)).

### A status dictionary ends label drift and colour-only meaning

Define one dictionary per aggregate: Order, Dispatch, Payment, Return and Purchase order. Each entry holds a stable code, an Indonesian label of one to three words in sentence case, a tone, an icon, who acts next, and a one-line description. `StatusPill` renders only from this dictionary, so CSS stops keying on label strings and the same word cannot mean different things in different modules. Atlassian's lozenge guidance says such labels are non-interactive and sentence case ([Atlassian](https://atlassian.design/components/lozenge/usage)). Carbon requires at least two of colour, shape and symbol, with icons paired with text and **3:1 contrast for status colours** ([Carbon](https://carbondesignsystem.com/patterns/status-indicator-pattern/)).

Order detail should show a horizontal happy-path stepper: Diajukan → Disetujui → Diterima toko → Disiapkan → Dikirim → Diterima divisi → Ditagih → Lunas. Branch states such as pending substitution, partial dispatch or rejected payment appear as exceptions on the stepper, not as extra steps. Below it, a vertical activity timeline merges ordering, fulfilment, payment and return events, each with actor, role, time, reason and a link to the related document. NN/g found that long silent gaps make users assume something went wrong and lose trust in the tracker, while fine-grained "joined the queue" updates reassure them ([NN/g](https://www.nngroup.com/articles/status-tracker-progress-update/)). So the timeline should record queue entry events ("Masuk antrean verifikasi Koperasi"). Sealed checkpoints can appear as a quiet "terverifikasi" marker, with no hashes shown by default.

### Unknown outcomes need their own state, never "Gagal"

Every system state needs a plain reason, what happened to the user's data, and the next action. Carbon defines three empty-state types: first use, no results from a user action, and data that exists but cannot be shown ([Carbon](https://carbondesignsystem.com/patterns/empty-states-pattern/)). NN/g puts skeletons on full-view loads under about 10 s, spinners on single modules waiting 2–10 s, and determinate progress beyond 10 s ([NN/g](https://www.nngroup.com/articles/skeleton-screens/)). GOV.UK error pages say what happened to the user's answers and avoid jargon and red warning text ([GOV.UK](https://design-system.service.gov.uk/patterns/problem-with-the-service-pages/)). Toasts that carry an action, and all errors, persist until dismissed ([Carbon](https://carbondesignsystem.com/patterns/notification-pattern/)). On a flaky network, the app should say what state the data is in and never block the whole UI with a modal ([web.dev](https://web.dev/articles/offline-ux-design-guidelines)). Conflicts surface as `412 Precondition Failed` on conditional writes ([MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/If-Match)). The UI keeps the user's input and shows who changed what, which NN/g's preserve-input rule also requires ([NN/g](https://www.nngroup.com/articles/error-message-guidelines/)).

The state Unit Toko most needs to standardise is **unknown outcome**: the request may have committed, but the response was lost. Stripe's semantics define the fix. A retry with the **same** idempotency key returns the saved result of the first request instead of performing the work twice ([Stripe](https://docs.stripe.com/api/idempotent_requests)). The frontend already references idempotency keys in about 85 source files and has an `OperationRecovery` workspace in administration (local codebase observation). The backend contract is therefore largely in place; what is missing is one consistent UX. No design system documents this pattern, so the table below combines the Stripe, GOV.UK and NN/g rules above.

| State | Trigger | UI (Indonesian copy) | Allowed actions |
|---|---|---|---|
| Mengirim | request in flight | button `aria-busy`, form locked | none |
| Tercatat | 2xx | "Persetujuan tercatat pukul 10.43 WIB (ref. APV-…)" with what happens next | view timeline |
| Ditolak sistem | 4xx validation | field errors plus linked summary, input kept | fix and resubmit (same key if content unchanged) |
| Konflik | 412 / version mismatch | "Pesanan ini diubah oleh Dewi (Kepala Toko) pukul 10.42 WIB setelah Anda membukanya" with field diff | load latest, review differences |
| Belum pasti | timeout, network drop, 5xx after send | neutral tone: "Kami belum dapat memastikan apakah persetujuan Anda tercatat." | **Periksa hasil**, which re-sends the original request with the original key |
| Offline | `navigator.onLine` false or fetch fails before sending | banner plus a "Belum terkirim" chip per item | automatic retry with the same key |

Two rules make this safe. The original submit button stays disabled while the outcome is unknown, so nobody can mint a new key. **A new key is issued only when the content changes**, because that is a new intent. Never label an unknown outcome "Gagal". That invites a second submission, and in a payments context a second submission is the expensive failure.

### Navigation by domain, homes by role, palette as accelerator

Use a left sidebar with visible text labels, grouped by domain: Belanja/Pesanan, Pemenuhan, Pembayaran, Retur, Pengadaan, Persediaan, Laporan, Administrasi. Show only the groups the user's grants allow, with "Pekerjaan saya" pinned at the top. NN/g shows that icon-only rails add clicks and that less-used items belong lower down ([NN/g](https://www.nngroup.com/articles/vertical-nav/)). Use breadcrumbs only where the hierarchy is three or more levels deep, and never make the current page a link ([NN/g](https://www.nngroup.com/articles/breadcrumbs/)).

Each role home should put operational, time-sensitive work first and analysis below it. NN/g separates operational dashboards, which inform time-sensitive tasks, from analytical ones ([NN/g](https://www.nngroup.com/articles/dashboards-preattentive/)). A Ctrl+K command palette that looks up by code and name (PO number, SKU, division, invoice) and offers permission-filtered verbs is a useful accelerator. Superhuman argues every action should be reachable from it ([Superhuman](https://blog.superhuman.com/how-to-build-a-remarkable-command-palette/)). But the evidence for palettes is practitioner writing, not research, so the palette supplements the sidebar and never replaces it. Keyboard shortcuts on triage desks (J/K to move, A to approve-review, R to reject with a reason) should appear next to their commands, where experts notice them and novices can ignore them ([NN/g](https://www.nngroup.com/articles/ui-accelerators/)). When a delegate is acting for someone, the header must always say so: "Bertindak sebagai: Kepala Unit (delegasi dari Budi)".

### Forms validate on blur, keep input, and treat rupiah as integers

Validate after the user finishes a field, not while they type ([NN/g](https://www.nngroup.com/articles/errors-forms-design-guidelines/)). In React Hook Form, `mode: "onTouched"` does exactly this: it validates on first blur and then live while the user fixes the field ([React Hook Form](https://react-hook-form.com/docs/useform)). Long forms add a GOV.UK-style error summary that receives focus and links each error to its field ([GOV.UK](https://design-system.service.gov.uk/components/error-summary/)). Its Indonesian heading is "Ada masalah", and each field carries `aria-invalid`, `aria-describedby` and a visually hidden "Kesalahan:" prefix. One zod schema per form, imported by both the RHF resolver and the server action, keeps client and server validation in step. The server action returns `{fieldErrors, formError}`, which is merged back with `setError`.

Use `type="text"` with `inputmode="numeric"` for whole numbers, with the unit or currency as a prefix or suffix ([GOV.UK](https://design-system.service.gov.uk/components/text-input/)). Two files still use `type="number"` (local codebase observation). Use steppers only for small adjustments ([Carbon](https://carbondesignsystem.com/components/number-input/usage/)). That suits cart and picking quantities. Procurement lines and count sheets need a keyboard-first grid. Pickers for SKU, division, vendor and user are async comboboxes that match both code and name ("BRG-00123 — Kertas A4 80g"). Carts, PO drafts, count sessions and return requests autosave with a visible "Tersimpan otomatis 10.42" indicator. Leaving the page offers Simpan / Simpan sebagai draf / Buang / Batal, adapted from SAP's draft handling ([SAP Fiori, via search summary](https://www.sap.com/design-system/fiori-design-web/v1-84/foundations/best-practices/global-patterns/object-handling/draft-handling)).

## Indonesian conventions and WCAG 2.2 AA fix copy, formats and contrast together

### Write as a "Tenaga Operasional": Anda, verb-first, no jargon

The national government design system (IDDS) chooses a writing voice through personas. Its operational persona, taken from INA Digital Edu, is efficient, neutral and solution-oriented, written in a light-formal, direct style. Its examples include "Data belum bisa disimpan. Periksa kembali kolom yang belum diisi." IDDS also bans phrases that assume ideal conditions, such as "klik saja", and status shown by colour alone ([INA Digital](https://design.inadigital.go.id/foundation/writing/)). Seragam sets two umbrella styles: "lugas" (plain and direct) and "formal tapi tidak kaku" (formal but not stiff). Its inclusive-writing table replaces vague verbs and raw error dumps with plain verbs and guidance on what to do next. It notes that screen-reader users often hear only the first sentence, so the action should come first ([Seragam](https://seragam.belajar.id/inklusivitas)). Localisation guides agree: use "Anda" with a capital A, drop the pronoun in instructions, and **never switch between Anda and kamu within a flow** ([FontLab](https://fontlab.dev/vexy-fontlab-writing-styleguide/fl1992mk/languages/id/); [Mozilla](https://mozilla-l10n.github.io/styleguides/id/index.html)).

Unit Toko is already compliant on register. "Anda" appears in 94 source files, and "kamu" and "Oops" appear in none (local codebase observation). The remaining work is consistency. Keep **a glossary with one term per concept**: choose "Pesanan" or "Order", and "Tagihan" or "Invoice", then use only the choice, while keeping the document names users already know (Surat Jalan, faktur pajak, bukti transfer). **Button labels** should be one to three words, an imperative verb plus its object ("Unggah bukti transfer", "Cetak Surat Jalan"), using the same verb as the dialog title. **Error messages** should name the field and the fix with real values ("Jumlah melebihi stok. Stok tersedia: 12 dus."). Use **"belum bisa…" rather than "gagal…"** where the problem is recoverable, and drop **developer words** such as "server", "timeout", "sync" and "500".

Telkom's Legion guideline adds two checks: text scans best at about 40 characters per line and three lines or fewer, and title, description and buttons should be read aloud together ([Legion](https://legion.digitaltelkom.id/content/writing-guideline)). Printed documents and WhatsApp text address the reader as "Bapak/Ibu".

### EYD V and Intl disagree on one space, and ICU versions disagree on decimals

EYD V writes rupiah as **"Rp" with no period and no space**, a dot for thousands and a comma for decimals: Rp1.250.000 or Rp1.250.000,00. It does not put dots in non-quantity numbers such as years and account or ID numbers ([Badan Bahasa EYD V](https://badanbahasa.kemendikdasmen.go.id/resource/doc/files/SK_EYD_Edisi_V_16082022.pdf); [Kompas](https://www.kompas.com/skola/copy/2023/06/13/080000669/bagaimana-penulisan-rp-rupiah-yang-benar-)). Clock times use a dot ("pukul 14.30"), and day and month names are capitalised ([EYD](https://ejaan.kemdikbud.go.id/eyd/penggunaan-tanda-baca/tanda-titik/)). Formal writing places the time-zone label after a space ("08.00 WIB") ([PTA Ambon](https://www.pta-ambon.go.id/portal/MATERI%20BIMTEK/FORMAT%20PENULISAN%20PUTUSAN-%20ketua.pdf)).

`Intl` with the `id-ID` locale gets the separators, month abbreviations (Jan … Agu … Des) and WIB/WITA/WIT labels right. It departs from EYD in two ways engineers must handle. It inserts a **U+00A0 no-break space after "Rp"**. And its **default number of IDR decimals changed between runtimes**: in the research runs, Node 24.3 printed "Rp 1.250.000,00", while Node 25.7 rounded 1,234,567.5 to "Rp 1.234.568" ([MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/NumberFormat/NumberFormat); research-time local execution). The consequence is direct. Server rendering and client hydration on different ICU builds can produce different strings, and any formatter that relies on defaults is a latent hydration-mismatch bug.

Today `Intl.NumberFormat` appears in 15 source files and `toLocaleString` in 38 (local codebase observation). Replace them all with one `lib/format` module that every screen uses:

| Function | Output and rule |
|---|---|
| `formatRupiah(n)` | `minimumFractionDigits: 0, maximumFractionDigits: 0`, NBSP stripped to match EYD (or kept deliberately, as long as one rule is applied everywhere); "Rp1.250.000" |
| `formatRupiahDocument(n)` | Adds ",00" and the amount in words ("terbilang") for kuitansi and Surat Jalan, which EYD allows in legal and receipt contexts ([EYD](https://ejaan.kemdikbud.go.id/eyd/penulisan-kata/angka-dan-bilangan/)) |
| `formatDate` / `formatDateLong` | "17 Okt 2026" in lists; "Sabtu, 17 Oktober 2026" in detail views |
| `formatTime` | "14.30 WIB", always with the zone |
| `formatRelative` | "kemarin", "2 jam lalu", with the absolute value in a tooltip |
| `formatPhone` / `toWaMe` | Display "0812-3456-7890"; link digits "628123456789" |
| `maskNik` / `formatNpwp` | Masked by default; no thousand dots |

Compact notation ("1,3 jt") is allowed only on KPI tiles, with the full value in a tooltip. Never use numeric-only dates such as 10/11/2026. Money is stored as integer rupiah, and the input parser treats "." as a thousands separator, because "1.250" typed by an Indonesian user means 1,250. NPWP fields must accept the legacy 15-digit format and the 16-digit format, plus the 22-digit NITKU for branches. The 15-digit form keeps legal force under PER-6/PJ/2024 ([DDTC](https://news.ddtc.co.id/literasi/kamus/1803684/apa-beda-nik-sebagai-npwp-npwp-16-digit-dan-nitku)). Masking NIK and NPWP is best practice. The research could not confirm a specific legal display obligation under the personal data protection law (UU PDP).

### Build for a 360-pixel Android and a 35% desktop share

Indonesia is Android-majority and mobile-first, but not mobile-only. **360×800 is the most common mobile viewport**, at 12.7% in January 2026 ([StatCounter](https://gs.statcounter.com/screen-resolution-stats/mobile/indonesia)), and about a third of Android devices still ran Android 10–12 that month ([StatCounter](https://gs.statcounter.com/os-version-market-share/android/mobile-tablet/indonesia/n%D0%9A%D0%B0%D0%BA)). More than half of the smartphones sold in Q3 2025 cost under US$200 ([Omdia via TelecomLead](https://telecomlead.com/smart-phone/indonesia-smartphone-market-sees-strong-competition-in-q3-2025-as-transsion-leads-shipments-123517)). Although 98% of internet users go online by phone, **51.2% also use a laptop or desktop, and desktop carries about 35% of web traffic**. Median mobile download speed reached about 45 Mbps in 2025 ([DataReportal](https://datareportal.com/reports/digital-2026-indonesia)), yet rural small businesses still name unstable internet as a top barrier and rate offline mode their most-wanted feature, at 4.52 out of 5 ([Iwan, Urindo](https://ejournal.urindo.ac.id/index.php/administrasimanajemen/article/download/7016/2798)).

The split by role follows. Staf Toko routes are designed and tested at 360px with the keyboard open. Approval, reconciliation and accounting get a real desktop layout of 1280px or more, because PICs and finance staff work on laptops. Tailwind v4 and Next 16 both need Chrome 111+ or Safari 16.4+ ([Tailwind](https://tailwindcss.com/docs/upgrade-guide)). A stale browser on an old device will render the app broken, so test on one Android 10–11 device as well as current Chrome and Samsung Internet. The roughly 170 KB gzipped first-load JavaScript budget for field routes is a working assumption, not an Indonesian benchmark. Set it, measure it and adjust it.

### WhatsApp points to the record; it never holds it

About nine in ten Indonesian internet users open WhatsApp every month ([Campaign Brief Asia on DataReportal](https://campaignbriefasia.com/2025/11/06/digital-2026-indonesia-reveals-social-media-user-identities-increased-26-to-180-million/)). Indonesian small-business case studies also document where WhatsApp ordering breaks down: slow or ignored admin replies, and managers unable to monitor stock and cash ([Jurnal Unpad](https://jurnal.unpad.ac.id/jane/article/viewFile/69427/27376)). So the app stays the system of record and WhatsApp is the pointer. `wa.me/?text=` opens a contact picker with pre-filled text, and `wa.me/<number>?text=` opens a specific chat ([WhatsApp](https://faq.whatsapp.com/5913398998672934/?locale=en_US)). Numbers must be written without "+", which failed on WhatsApp Web in practitioner testing ([Technically Product](https://www.technicallyproduct.co.uk/messaging/international-number-formats-that-do-and-dont-work-in-whatsapp-click-to-chat/)).

The codebase has no WhatsApp integration yet. Add two things. First, a "Bagikan ke WhatsApp" button on order, Surat Jalan and invoice pages, which shares a short, formal summary and a link back to the app. Second, a "Hubungi via WhatsApp" help link in the same place on every page, which also satisfies WCAG 3.2.6 Consistent Help. Pre-filled text must never carry prices, NIK/NPWP or bank details, which would persist in chats. WhatsApp must never be the only notification channel or be treated as proof.

### Perceived complexity is the adoption lever the team controls

A 2026 survey of 177 Indonesian cooperatives found that **perceived complexity, relative advantage, top-management support and vendor support** drive actual use. It cites Ministry data putting cooperative staff readiness for digitalisation at only **30–40%** ([Putri et al.](https://www.tandfonline.com/doi/full/10.1080/23311975.2026.2700803)). In Purbalingga, **4 of 5** small businesses kept using a POS system on their own after training and a mobile-friendly PWA. The one laggard needed ongoing mentoring ([Prasetyo et al.](https://doi.org/10.22437/jkam.v7i1.21453)). KSU Visiana Bhakti, a cooperative with its own "Unit Toko" serving TVRI staff, moved from manual records to Excel to POS in stages, migrating its existing records along the way ([Maryam et al.](https://doi.org/10.32670/ecoopsday.v5i2.4696)).

The design implications are concrete. Shop staff get role homes with three or four large entry points. Advanced filters sit behind "Lainnya", and each screen has one primary action. Defaults, pickers and "Ulangi pesanan" replace typing; the repeat-order button also serves WCAG 3.3.7 Redundant Entry. Excel import and export, and print layouts that look like today's handwritten Surat Jalan, bridge existing habits.

Beyond the software, the rollout should include laminated one-page "Cara…" cards per role, two-to-three-minute task videos, a named internal champion, weekly check-ins in the first month, and a parallel paper-and-app period with a fixed cut-over date. Track the share of orders entered in the app as the adoption metric.

### Current colours fail WCAG 2.2 AA in four places

WCAG 2.2 adds nine success criteria and removes 4.1.1 Parsing ([W3C](https://www.w3.org/WAI/standards-guidelines/wcag/new-in-22/)). The new ones that bite here are **2.4.11 Focus Not Obscured** (sticky headers and bottom action bars), **2.5.7 Dragging Movements** (drop zones and any drag-to-reorder), **2.5.8 Target Size** of at least 24×24 CSS px, **3.2.6 Consistent Help**, **3.3.7 Redundant Entry**, and **3.3.8 Accessible Authentication**, which requires allowing paste and password managers and forbids puzzles.

Indonesia has no binding WCAG-based regulation for a private cooperative's internal app. But IDDS follows WCAG 2.2 and audits itself at AA ([INA Digital](https://design.inadigital.go.id/foundation/accessibility/)), and Komdigi's 2025 website evaluations used WCAG 2.2 criteria ([JDIH Komdigi](https://jdih.komdigi.go.id/berita/view/111)). That makes **WCAG 2.2 AA the de-facto national benchmark**. Present it as alignment with IDDS, not as a legal requirement. IDDS's own audit found four main problems: focus visibility, text contrast, colour-only status, and inconsistent keyboard navigation. Unit Toko's legacy CSS has the same profile.

Contrast ratios computed from `globals.css` values, using WCAG's relative-luminance formula against the thresholds of 4.5:1 for text and 3:1 for UI components and focus indicators ([W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/)):

| Element (current value) | Ratio | Requirement | Result |
|---|---|---|---|
| Status badge "menunggu" `#b47c37` on `#fff3e1` (12px) | 3.26:1 | 4.5:1 | Fail |
| Status badge "diproses" `#547eaf` on `#eaf2ff` | 3.74:1 | 4.5:1 | Fail |
| Status badge "selesai" `#3e8b74` on `#e7f5f1` | 3.64:1 | 4.5:1 | Fail |
| Status badge "ditolak" `#ba6457` on `#fff0ee` | 3.75:1 | 4.5:1 | Fail |
| Muted meta text `#83969e` / `#8a9ca4` on white | 3.08:1 / 2.85:1 | 4.5:1 | Fail |
| Table header text `#7c919a` on `#f7fafb` | 3.14:1 | 4.5:1 | Fail |
| Focus outline `#ed7829` on white / on page `#f2f6f7` | 2.87:1 / 2.64:1 | 3:1 | Fail |

Later override files may restyle a few of these selectors, so an axe run should confirm the rendered values. The badge rules, however, carry `!important`, so they almost certainly win today. The fix belongs in the token file: darker status foregrounds, a muted-text token of at least 4.5:1, and a focus ring at least 2px wide with 3:1 contrast against both white and the page background (a dark teal works better than orange). A script then checks every token pair in CI.

The rest is mechanical. Set `scroll-padding` equal to the height of sticky bars (2.4.11), put a "Pilih file" button beside every drop zone (2.5.7), give table icons 24px hit areas and touch-screen primary actions 44–48px (2.5.8), add `autocomplete="current-password"` and `"one-time-code"` (3.3.8), and show status as text plus icon, never colour alone. `<html lang="id">` is already set (local codebase observation).

## Field workflows must assume Android phones, weak signal and gloves

### Payment proofs: screenshot-first upload with OCR-safe compression

Most transfer proofs are m-banking screenshots, so the primary action is "Unggah screenshot / file" using a plain `<input type="file">`, with "Foto bukti (kamera)" as a secondary action. Desktop adds a large, always-visible drop zone. GOV.UK's redesigned upload component moved in the same direction ([GOV.UK](https://design-system.service.gov.uk/components/file-upload/)), and web.dev recommends starting from the plain input and enhancing it ([web.dev](https://web.dev/articles/media-capturing-images)). List `image/jpeg` first in `accept`. iOS Safari transcodes to the first non-wildcard type, which turns HEIC photos into JPEG that Tesseract can read ([WebKit](https://bugs.webkit.org/show_bug.cgi?id=292350)). Reuse GOV.UK's error templates in Indonesian ("File harus berupa JPG, PNG atau PDF", "File harus lebih kecil dari 5 MB").

Compression must protect OCR, not just bytes. Tesseract performs best at 300 DPI or more on deskewed input ([Tesseract](https://tesseract-ocr.github.io/tessdoc/ImproveQuality.html)), Veryfi treats a width or height of 500px or less as a reliability risk ([Veryfi](https://faq.veryfi.com/en/articles/5429636-blur-detection)), and Uppy's compressor defaults to quality 0.6, a setting chosen for size ([Uppy](https://uppy.io/docs/compressor/)). So downscale photos only to a long edge of about 2,000–2,500px at quality 0.8 or higher, leave screenshots nearly untouched, warn below about 1,000px on the short edge, reject below 500px, and bake EXIF rotation into the pixels before the server's OCR sees them.

For resilience, give each selected file its own idempotency key, retry with backoff, show per-file progress, and keep pending files in IndexedDB as Uppy's Golden Retriever does ([Uppy](https://uppy.io/docs/golden-retriever/)). Retry on the `online` event or the next app open, because **Background Sync does not exist in Safari or Firefox** ([caniuse](https://caniuse.com/background-sync)). "Ganti" (replace) creates a new sealed version and never overwrites the old one.

### OCR review accelerates matching but the bank mutation check stays mandatory

A confidence score alone misleads. Nutrient documents a 0.97-confidence extraction taken from the wrong column, and the error only became visible when the source region was highlighted ([Nutrient](https://www.nutrient.io/blog/document-extraction-confidence-scores/)). Taggun says its score is not a calibrated probability, and returns pixel regions for overlay ([Taggun](https://developers.taggun.io/docs/confidence-levels)). Tesseract already emits a bounding box and word confidence for every word in hOCR and TSV output ([Tesseract](https://tesseract-ocr.github.io/tessdoc/Command-Line-Usage.html)), so Unit Toko can build grounded review without a new engine.

Today `PaymentOcrPanel` shows a raw percentage per field (local codebase observation). Replace it with a reviewer desk. About 60% of the width is a document viewer with zoom, rotate and an OCR-box toggle. The rest holds four field cards: Nominal, Tanggal/Jam, No. Referensi and Rekening/Nama Penerima. Each card shows the suggested value, a **composite** confidence chip (Tinggi / Periksa / Rendah), the reason for any flag ("nominal ≠ total pesanan Rp1.250.000"), and the expected value. The composite combines three signals: the lowest word confidence among the tokens used; whether the value parses (an IDR integer, a valid date, a reference matching the bank's pattern); and cross-checks against the order (amount equals total, beneficiary equals the cooperative's account, date falls inside the order window). Any failed high-impact cross-check routes the item to manual review whatever the OCR score. Focusing a card highlights its boxes on the image.

The keyboard flow is built for speed. Tab or J/K moves between fields, Enter accepts the suggestion, typing overwrites it and Esc reverts it. Ctrl+Enter approves, and is enabled only when all four fields are confirmed. Rejection uses reason chips ("buram", "terpotong", "bukan bukti transfer", "nominal tidak sesuai"). The desk shows the queue position ("3 dari 12") and advances automatically, and every correction is logged as suggested → corrected.

Duplicate detection should be layered ([Peakflo](https://peakflo.co/blog/duplicate-expense-claim-detection-employee-reimbursements)). Hard-block identical file hashes and identical reference-plus-amount pairs. Only flag perceptual near-matches, since m-banking screenshots from the same bank look nearly identical and false positives are likely. Tell the buyer only that the proof resembles an earlier one and finance will check, never "fraud". Above all, BCA has warned through Kompas TV that **AI-edited fake transfer proofs are increasingly convincing**, and that no proof should be trusted until the receiving account's mutation is checked ([Kompas TV](https://www.kompas.tv/ekonomi/589498/modus-penipuan-bukti-transfer-palsu-makin-canggih-berkat-ai-cek-langkah-pencegahannya)). OCR speeds up matching. It never replaces the bank statement check.

### Native capture for photos, live camera only for scanning

For one-off photos, such as a proof photo or a wet-signed Surat Jalan, `<input type="file" accept="image/*" capture="environment">` opens the native camera without any permission UI. It is supported on iOS Safari and on Chrome and Firefox for Android ([caniuse](https://caniuse.com/html-media-capture)). Use `getUserMedia` only for live scanning. It requires HTTPS and consent, and the track should be stopped when idle ([web.dev](https://web.dev/articles/media-capturing-images)). Use `facingMode: {ideal: "environment"}` rather than `exact`, which fails outright when no rear camera exists ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/MediaTrackConstraints/facingMode)).

iOS Home-Screen web apps are a live hazard. WebKit bug 327237, filed on 12 Oct 2026, reports camera permission prompts again on every launch, and on `pushState` navigation ([WebKit](https://bugs.webkit.org/show_bug.cgi?id=215884)). Until it is fixed, mount the scanner as a persistent overlay outside the changing route segment, reuse one `MediaStream`, and recommend that iOS staff use a Safari tab with camera access set to "Allow". Show a priming card before the permission request, and recovery steps written per platform after `NotAllowedError`. Skip document auto-capture for now. OpenCV.js weighs about 8 MB, struggles on cluttered backgrounds ([Dynamsoft](https://dynamsoft.com/codepool/web-document-scanner-with-opencvjs.html)), and most proofs are screenshots anyway.

### One scanner hook serves camera, keyboard-wedge and manual entry

As of October 2026, `BarcodeDetector` works natively on Chrome for Android and Samsung Internet. It is only partial on Chrome desktop, because Windows lacks it, and it remains **disabled by default on every Safari and iOS version** ([caniuse](https://caniuse.com/mdn-api_barcodedetector); [Chrome](https://developer.chrome.com/docs/capabilities/shape-detection)). The `barcode-detector` package fills the gap with ZXing-C++ WebAssembly. Self-host its `.wasm` rather than letting it load from jsDelivr ([GitHub](https://github.com/Sec-ant/barcode-detector)). Avoid zxing-js, which is in maintenance mode ([GitHub](https://github.com/zxing-js/library)), and html5-qrcode, whose maintainer is seeking new owners ([GitHub](https://github.com/mebjas/html5-qrcode)).

USB and Bluetooth scanners act as keyboard wedges. Configure a carriage-return suffix, and debounce about 100 ms between scans as Odoo does ([Odoo](https://www.odoo.com/documentation/18.0/applications/inventory_and_mrp/barcode/setup/hardware.html)). Distinguish scans from typing by keystroke speed: onScan.js defaults to 30 ms per character and a minimum length of 6 ([onScan.js](https://unpkg.com/onscan.js@1.5.2/README.md)). The `navigator.vibrate` API is absent on iOS ([caniuse](https://caniuse.com/vibration)), so feedback has to be sound plus a visual flash.

The result is one `useScanner()` hook with three sources feeding the same `onScan(code, source)` handler. The first is a wedge listener that is ignored while focus is in a free-text field. The second is the camera, using native detection or the polyfill, requesting at least 1280×720 and showing a torch toggle where the device supports it. The third is a manual GTIN field with check-digit validation. Each scan validates the GTIN check digit and looks the code up before accepting it. A success gives a short beep and a green banner with the product name and the new count. An error gives a distinct double beep and a red banner that stays until acknowledged. For heavy receiving or stock counts, a cheap Bluetooth ring scanner is often the biggest UX gain. Commercial SDKs such as STRICH or Scandit are the upgrade path if damaged labels or low light defeat the free stack ([STRICH](https://strich.io/comparison-with-oss.html)).

### Receiving, picking and dispatch follow the scan-increment-validate model

WMS barcode apps share one model. The worker opens a task. Scanning a product adds one unit; scanning a pack barcode adds the pack quantity. A line editor offers +1/−1, a "+#" button that fills the expected quantity, and a keypad. A single Validate ends the task, and short quantities trigger a backorder prompt ([Odoo](https://www.odoo.com/documentation/18.0/applications/inventory_and_mrp/barcode/operations/receipts_deliveries.html)). Unit Toko should copy this. **Receiving** starts with "Hitung koli", a large counter with a one-tap "Sesuai (N koli)", then moves to "Periksa isi", with lines sorted by shelf and a progress bar per line. Exceptions sit in a sticky bottom sheet (Kurang, Lebih, Rusak with a required photo, Salah barang), and Validate asks whether to receive the partial quantity and create a backorder. **Picking** shows one task at a time in shelf order. A wrong scan raises a blocking banner ("Bukan barang ini – ambil X dari Rak B2"), and a short pick requires a reason that feeds the existing substitution flow. **Dispatch** binds each koli QR label to the Surat Jalan, which itself carries a QR for the recipient.

Touch ergonomics go beyond WCAG's 24px minimum ([W3C](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)). Primary actions of 48px or more sit in the thumb zone, quantities use large type, and no gesture needs two hands. The 48px figure is a design inference for gloved use, not a researched threshold.

Offline, queue **scan events, not final state**, in IndexedDB, each with a client UUID, and replay them idempotently. Show a persistent "3 aksi belum tersinkron" chip. Keep Validate server-only, because sealed records should not be finalised from a device that cannot reach the seal authority.

### Delivery proof binds authenticated identity and metadata to the Surat Jalan

Logistics platforms let an administrator set signature, photo and notes to required, enabled or disabled per task, and block completion until the required items are captured ([Onfleet](https://docs.onfleet.com/reference/completion-requirements)). Indonesian law gives an electronic signature the same standing as a manual one, but an **uncertified signature, one not issued through a licensed certification provider (PSrE), has weaker evidentiary weight and is proven by forensic examination** ([Hukumonline](https://www.hukumonline.com/klinik/a/begini-pembuktian-tanda-tangan-elektronik-di-pengadilan-lt62444b29a4d00)).

Unit Toko's e-POD flow should therefore capture metadata as well as a scribble. The staff member scans the Surat Jalan QR, confirms the koli count with one tap, and enters the recipient's name and position with autocomplete from the division's known PICs. The recipient signs on a full-width canvas scaled by `devicePixelRatio`, remembering that rotation clears the canvas ([signature_pad](https://github.com/szimek/signature_pad)), or the staff member takes a native-capture photo of the wet-signed Surat Jalan. Exceptions are recorded with photos. The submission stamps server time, device time, GPS if permitted, the user, and hashes of the signature and of the Surat Jalan version.

The strongest variant is a **QR handoff**: the recipient scans the Surat Jalan QR with their own phone and taps "Konfirmasi terima" in their own authenticated session. That ties receipt to an account rather than a drawing. Whether a photographed wet signature counts as an electronic signature remains legally unresolved in the sources found.

### Stock opname counts blind and approves separately

Odoo shows the trade-off clearly. "Leave Empty" forces the counter to type what they counted, while "Set Current Value" only asks them to verify the existing number ([Odoo](https://www.odoo.com/documentation/18.0/applications/inventory_and_mrp/inventory/warehouses_storage/inventory_management/count_products.html)). NetSuite sends completed counts to a supervisor, whose rejection returns the count for recounting ([NetSuite](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_155993310131.html)).

Unit Toko's opname should run in four stages. To **plan**, the supervisor creates a session per area, and the system snapshots the book quantity and prints count sheets in shelf order. Counters then **count blind by default**: they scan to increment or type quantities, and see only their own running totals. In **variance review**, the supervisor sees book versus counted quantity, in units and in rupiah at cost, sorted by absolute size, and lines above a threshold are flagged for recount, preferably by a different counter. Only after **approval** are sealed adjustments posted, each with a reason code.

Uncounted items are listed explicitly ("Belum dihitung (12)") and **never zeroed silently**. A non-blind "verifikasi" mode is acceptable for quick cycle counts of low-value items, provided the audit log marks it. Blind counting is slower, and no study quantifying its accuracy advantage was found. The control argument, separating the counter from the expected number, is what justifies it.

## Conclusion

The research changes where the effort should go. The instinct is to redesign screens. The evidence points instead to fixing the cascade's priority order and the shared contracts first. Once legacy CSS sits below Tailwind's layers and tokens own colour, type and density, the shadcn primitives already in the repo start to win, and every later screen migration becomes a deletion rather than another override. The same logic applies to behaviour. Unit Toko already has the hard backend semantics: idempotency keys, optimistic concurrency, server-side authorization and sealed checkpoints. What users lack is a consistent way to *see* those guarantees: an "unknown outcome" state that re-sends the same key, a stale-approval banner, a self-approval explanation, a timeline with sealed checkpoints. That is the cheapest way to make the system feel trustworthy to staff whose digital readiness sits at 30–40%.

Two risks deserve explicit management. First, OCR and confidence scores will tempt the team to automate payment verification just as forged transfer proofs are getting better. The design must keep the bank-mutation match as the gate and use OCR only for speed. Second, the device mix is split, not uniformly mobile. Finance and approval work happens on laptops at desktop density, while field work happens on low-end Android at 360px with gloves and weak signal. A single "responsive" compromise would serve both poorly, so density modes and role-specific homes are core requirements.
